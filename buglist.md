## Fixed

- **BUG-010 — infinite loop in parser error recovery (OOM).** `recover()` could return
  without consuming a token (at a `}` or a statement keyword). `parseProgram` then
  re-parsed the same failing statement forever, growing `errors[]` until the process died
  with a heap OOM. `npm run build` reported success because the child's exit code was
  lost. Fixed by forcing forward progress when recovery does not advance.
  Trigger: `src/cli/commands/db.no` — 1 of only 4 files in `src/` the compiler could not
  compile. Both the TS and the self-hosted parser carried the bug.

- **BUG-010b — `fn` not supported in expression position.** `items.filter(fn(f) { ... })`
  failed with "Expected expression" and the statement was silently dropped from the AST
  while only an error was recorded, so the file compiled to empty output instead of
  failing loudly. Added `FunctionExpression` (parser + codegen), including the
  `fn*(...)` generator form and the implicit-return rule.

- **BUG-011 — object spread `{ ...src }` not parsed.** `parseObjectExpression` had no
  `...` case, so every object literal with a spread failed with "Expected property key";
  recovery then produced a top-level `return`, which is invalid JS and broke the
  self-hosted build. Spread is used throughout the Nodeon sources.

- **BUG-011b — arrow with an object-literal body emitted invalid JS.**
  `x => { ...x, k: v }` is a *block* in JavaScript, so the braces made `...spread` a
  syntax error. The generator now parenthesises an object body: `x => ({ ...x, k: v })`.

- **BUG-011c — bare-parameter arrow `x => body` unsupported.** A pre-existing gap with
  nothing to do with spread: `c => { ... }` failed for every body shape. Now supported.

- **BUG-012 — `x = v` always parsed as a declaration.** Nodeon's headline feature
  (`x = 10` with no keyword) produced a `VariableDeclaration` for *every* occurrence, so
  a re-assignment looked like a redeclaration. The emitted JS was correct — which is why
  600+ tests passed — but every AST consumer was misled. The optimizer then promoted an
  accumulated variable to `const` and dropped the accumulation:
  `let t = 0; for (v of a) { t = t + v }` → `const t = 0; for (v of a) { const t = t + v }`.
  A first use now declares; every later use assigns.

- **COMP-OPT — unsound constant propagation and let→const promotion.** Integrated with
  fixes: a binding that is ever reassigned is never replaced by its initialiser and is
  never promoted to `const`.

- **COMP-OPT — indexed-loop rewrite dropped non-array iterables.** The upstream version
  rewrote `for x in y` into `for (let i = 0, len = y.length; ...)` whenever `y` was a
  bare identifier. `Set`, `Map` and generators have no `.length`, so those loops became
  silent no-ops. Deliberately NOT merged; `for...of` is kept.

## WASM backend (non-JS target)

The WASM backend is the only route out of JavaScript, so its state matters as
much as the JS generator's. Measured by instantiating each module in a real
`WebAssembly` engine and calling it — not by inspecting bytes. Baseline was
8 of 16 language cases correct, with 3 modules the engine refused outright.

- **BUG-WASM-1 — a comparison result was typed as f64.** `emitInst` chose the
  operand type from the *destination local* rather than the operator. A
  comparison yields `i32` even when both operands are `f64`, so `a < b` pushed
  i32 operands and then emitted `f64.lt`, and the engine rejected the module:
  `local.set[0] expected type f64, found f64.lt of type i32`. Emitting operands
  at their own type, plus converting the i32 result when the destination is f64,
  fixed it.

- **BUG-WASM-1b — `&&`, `||` and bitwise ops fell through to `f64_add`.** In the
  f64 branch of `getBinOpcode` they had no case, so `a && b` on two f64s
  produced a float sum that was then stored where an i32 was expected. They are
  integer in wasm, so their operands are now narrowed first.

- **BUG-WASM-2 — `lowerFunction` passed the ENTRY block for every statement.**
  Anything after an `if` was appended to the entry block, the `if` arms were
  never wired, and `__continueBlock` was assigned but never read. `while` and
  `for` were not lowered at all — they fell into the "unsupported statement"
  default. Replaced with a `BlockBuilder` that owns a mutable current block and
  starts new ones at each control transfer. The IR block graph is now correct.

- **BUG-WASM-2b — the emitter emitted an EMPTY `if`/`end` for every branch and
  nothing for every `jump`.** Decoding the generated bytes showed the shape
  exactly: condition evaluated, `if`/`end` with no body, then the loop body
  emitted as a sibling — so both `if` arms ran and a loop ran once. Loops need
  a `br`, and in wasm a `br` is a BRANCH to the Nth enclosing `block`/`loop`/
  `if`, not a goto. Two consequences, both found by reading the decoder output:
  - A back edge is `br 0` to the `loop`, and the conditional exit is
    `br_if 1` — but with only the `loop` open there is no depth 1, so the whole
    loop is wrapped in a `block`: `block { loop { cond; eqz; br_if 1; body;
    br 0 } }`. Without the `block` the engine rejected the module.
  - The condition must reach the stack as an i32 *before* `eqz`; emitting a
    second `trunc` for an already-converted value also produced a rejected
    module.
  - A function whose every path returns (an `if` with a `return` in both arms)
    still needs a terminal return, or the validator reports "expected 1
    elements on the stack for fallthru". It is unreachable but it types the
    fallthrough.

- **BUG-WASM-3 — an `if` with no `else` ran both arms.** The merge block is the
  branch's else target, so the emitter executed the guarded `return` *and* the
  fallthrough: `if x > 0 { return 1 }  return 0` returned 1 for every `x`.

### WASM backend: state

**The data model is complete.** Numbers, strings, arrays, objects, control flow
(`if`, `while`, `for` over a range *and* over an array), and calls all compile
to a module a real `WebAssembly` engine accepts, and run.

| Nodeon | In linear memory |
|---|---|
| string | UTF-8 bytes, NUL-terminated; identical literals share an address; address 0 is null |
| array | `[len: i32][pad: i32][elem0: f64]…`, so `a[i]` is `f64.load(base+8+i*8)` |
| object | one 8-byte slot per field, offsets declared module-wide |

**Objects and arrays are bump-allocated, per evaluation.** The allocator is a
pointer stored *in memory* rather than a wasm global, so the encoder needs no
global section: `aligned = ptr - (ptr & 7); store(HEAP_PTR, aligned + size)`.
Field offsets are declared for the whole module before any function is compiled,
so an offset never depends on which function mentions the field first — a layout
that reused offsets would have returned `o.c` as the value of `o.b`. Arrays used
to be interned into the static data image instead, which made every `[]` in a
program the same list; see BUG-WASM-7.

A record field's WIDTH is also decided for the whole module: a field holding an
address is an `i32` slot, everything else an `f64` slot. Writing every field as a
double and reading an address back with `i32.load` takes the low 32 bits of a
double, which are zero for every address in this heap.

**Array iteration reuses the `while` shape.** A `for` over an array reads the
length header and strides 8 bytes per element, so it lowers to the same block
graph the emitter already encoded for `while`. Before this, a non-range iterable
compiled to a loop that never ran.

The uniform rule is that **every value that is not a number is an i32 address**.
That is exactly the shape the same code would take in a native backend, and it
opens the host seam: write a block into the exported memory, pass its address,
and compiled Nodeon reads it.

Whether a value is an address is decided by `inferModuleAddressTypes`, once for
the whole module and iterated to a fix point, because the fact crosses function
boundaries — see BUG-WASM-7 item 6.

What remains is the standard library — array methods such as `map`/`filter`
need it, and this backend does not link it — and the allocator's ceiling
(BUMP-WASM-8). Tracked in buglist.md.

`tests/wasm.test.ts` asserts every working case by RUNNING it in a real
`WebAssembly` engine, and `tests/program.test.ts` runs the whole of
`examples/life.no` through both backends against a hand-written reference. A gap
stays visible instead of quietly passing.

### BUG-WASM-8 — a record could be smaller than its own field offsets (fixed)

**Closed.** Field offsets come from ONE index space shared by the whole module,
so that a field's offset never depends on which function mentions it first. The
cost of that choice was paid wrong: a record was sized by **its own** field
count.

```no
fn f() { const o = { item: { v: 3 } }\n return o.item.v }   // answered 3.000000000029104
```

`v` had already taken index 0, so `item` got the shared offset 8 — one slot past
the end of an 8-byte record. `o.item` read the NEXT allocation, and the answer
came back as a double with a pointer spliced into its low half: `3` read as
`3.000000000029104`, which is `0x4008000000010000` where it should have been
`0x4008000000000000`.

Every record now reserves a slot for **every field name in the module**, and the
names are collected from the object literals too, not only from reads and
writes, so the count is closed before any function is emitted. The waste is
bounded by the number of distinct field names, which is what the shared layout
already implied.

**How it was found:** the symptom was a number that was *almost* right, which is
the worst kind. `3` versus `3.000000000029104` says "a few bits are wrong" and
points at precision; the low 32 bits of the result were `0x00010000` — the heap
start — which says "something read the wrong 8 bytes". Reading the linear memory
settled it in one step: the record really was 8 bytes and the offset really was
8.

### BUG-WASM-14 — what the repository's own source found (fixed, and it reframed the work)

The measurement that says what the backend is worth: compile every `.no` file in
`examples/` and `src/` and see how many produce a module a real engine accepts.
It is `tests/corpus-scan.test.ts`, opt-in because it compiles the whole repo:

```
NODEON_CORPUS_SCAN=1 npx vitest run tests/corpus-scan.test.ts
```

**The first number was a lie, and finding out why is the useful part.** It read
*19 valid, 16 invalid, 1 compiler crash*. Nineteen of those "valid" modules were
built from functions whose bodies had been silently replaced: a statement the
lowering did not support became a placeholder string, a function whose returns
all sat inside one compiled to VOID, and its callers used a value that was never
produced. The module validated. It was not a program.

So the lowering now **names** what it cannot do, and the file does not compile:

```
files 50 · valid 1 · invalid 0 · parse 0 · diagnostics 49 · threw 0
  32  sentencia "ImportDeclaration"
  12  sentencia "ExportDeclaration"
   3  sentencia "ClassDeclaration"
   1  sentencia "SwitchStatement"
   1  sentencia "DoWhileStatement"
```

One file compiles: `examples/life.no`, the one written for this backend.

**Forty-four of the fifty are blocked by MODULES.** That is the next piece of
work, and it came out of the measurement rather than out of an opinion: a
backend that cannot link two files cannot run this language at all, and every
other gap on the list is a footnote until that is done. The JS backend already
does it, so the semantics are settled — the WASM backend has to link them.

**Four defects the corpus found that no list of features would have produced:**

1. **A function that returns NOTHING.** The uniform thunk signature promises two
   values whatever the callee did, and a void function leaves the stack empty —
   so the thunk did a `local.set` with nothing to store. `examples/hello.no`
   was an invalid module.
2. **A method looked up on the prototype chain.** `method in LIST_METHODS` also
   answers true for anything on `Object.prototype`, so `code.toString(16)`
   matched and the lowering called `.replace` on a FUNCTION.
3. **An `else` on a void `if`.** An `else` is only valid on an `if` with a result
   type, and this emitter writes a void one. When the then-arm ended in a
   `return` the else arm was empty and the `else` made the module invalid.
4. **An arm that swallowed the next one.** An arm is finished when it RETURNS
   *or* when it jumps to the merge point, and only the second was recognised — so
   an arm that returned ran on and consumed the else arm. Every
   `if (c) { return a } else { return b }` compiled to the then-arm alone and
   answered 0 on the other branch. **It compiled, ran, and was silently wrong**,
   which is worse than the three that failed loudly.

**And one class fixed structurally rather than case by case:** an IR instruction
the emitter has no case for emitted NOTHING, and the module failed much later
about a stack somewhere else. `emitInst` now records the op and the compile
refuses with the name of every one it met.

**How the measurement is kept honest:** it is a gate, not a throwaway probe, and
it asserts only that the compiler never THROWS on real code — every other
outcome is a reported gap. A gate that failed on "44 files need modules" would
be a gate nobody could turn green, and a gate that passed on it was passing on
nothing.

### BUG-WASM-18 — the emitter could not jump OUT of a construct (fixed)

**Closed.** `break` and `continue` work, including a `break` from an `if` nested
two levels deep inside a loop.

The loop was already emitted as `block { loop { … } }`, so a `break` is `br 1` out
of the `block` and a `continue` is a `br` to the `loop` — **one level less**.

**The first attempt hung the whole suite, and the reason is the lesson.** It
stored the depth as a constant and emitted `br 1` at the top of a loop body. `br 1`
there targets the **loop**, so it re-enters it forever: the test never finished
rather than failing.

- The depth is **not a constant**. It is one more for every `if` or `block` the
  jump happens to sit inside, so it has to be computed **where the jump is
  emitted**, from the constructs opened since the loop: `N = openDepth - base`,
  plus one for the `block` a `break` leaves through.
- **A hang and a wrong answer are the same defect wearing different clothes.** The
  first attempt produced a hang; the second, a `br` that returned the wrong
  number. Neither shows up as a type or a validation error.

The lowering publishes a `scopes` stack so a `break` or a `continue` knows where
to go, and the emitter publishes the loop's exit and its `openDepth` while its
body is emitted. The gate then found a second thing the same change had been
hiding: a `continue` in a `for` loop was reported as "outside a loop", because the
`for` lowering never published a scope. A `for`'s `continue` goes to its STEP.

**Still open:** `switch` is the same jump with one more wrapper — the chain of
comparisons needs a `block` of its own for a `break` to escape, and it is the one
construct here still emitted as a flat list rather than by a dedicated emitter.

### BUG-WASM-20 — `switch`: the `br` depth, and the else arm found by position (fixed)

A `switch` lowers to a chain of comparisons — one `if/else` per level. That is
exact for this language, not a simplification: the JS backend states in one line
that cases are block-scoped with **no fall-through**, so every case body leaves,
and a chain of tests is the whole construct. It needs a `block` around the chain
for a `break` to leave through, and the lowering marks the first test with
`switchExit` so the emitter knows to open one.

**The `br` depth was off by one, and the previous two attempts were off by one in
opposite directions.** That is the signature of a wrong CONSTANT, not a misplaced
base — and the constant was `+ 1`:

```
br (openDepth - base) + 1
```

A loop opens two constructs, a `block` and a `loop`, and its `break` leaves the
outer one — so the `+ 1` is right for a loop. A `switch` chain opens **one**. Copy
the formula and the branch is one level too far out, and one level too far out
from inside a case is not a near miss: it is the **function body**, which wants a
result value on the stack, so the engine rejects the module. Two bases cannot fix
a wrong constant.

The fix removes the constant. A scope now records the `openDepth` of each thing a
jump can actually target — the `block` a `break` leaves, the `loop` a `continue`
re-enters — and the depth is `openDepth - thatTarget`:

```
br (openDepth - targetDepth)
```

`1 + 10 + 100 + 100` vs `222`: one of those is the compiler and one is me, and
the probe was wrong. Worth stating because the first draft of the probe expected
`222` for a loop that adds 1, then 10, then 100 twice — and the temptation at
that point is to "fix" correct code. **A test that says what is right is worth as
much as the fix that makes it pass.**

**A second defect was hiding behind the first.** `elseLabel` names the MERGE, and
the emitter found the else arm by POSITION — one block after the last block of the
then arm. Position is not knowable: `armBlocks` stops at an arm's jump to the
merge, so an arm holding a nested `if` does not end there. The emitter read a block
from the *middle* of the then arm and emitted it a second time as the else. In a
`switch` that meant the default ran whatever the case did:

```
n=7 → 70   ✓
n=8 →  0   ✗ want 5      (the default's body, emitted into the wrong arm)
```

So `IRBranch` grew an `elseArm` field: the lowering created the block, so the
lowering names it. `elseLabel` naming the merge and `elseArm` naming the arm are
two different facts, and conflating them is what the old code did.

**Also found, and named rather than half-solved:** a `continue` inside a `switch`
lands on a point *after* the switch, and a `br` can only reach an *enclosing*
construct. Every construct in between is an `if` inside the switch's own `block`,
so the jump has no target at all. It is a diagnostic now. Measured first: **0 of the
corpus's 31 switches contain a `continue`**, and 5 contain a `break` — which the
design handles, because a `break`'s depth is computed from the scope that owns the
label, wherever that scope sits in the stack.

**Measured, on the engine:**

| case | before | after |
|---|---|---|
| switch on a record field, string discriminant | diagnostic | 10, 20, 30 |
| `break` out of a case | invalid module | 100, 200, 300 |
| `break` two `if`s down | invalid module | 70, 5 |
| no fall-through between cases | invalid module | 1, 10, 100 |
| no `default` | invalid module | 1, 2, 0 |
| switch at the top of a loop body | invalid module | 211 |
| `break` out of a loop from inside a switch | **hung** | 3 |
| switch inside a switch | invalid module | 11, 90 |
| discriminant evaluated once | invalid module | 1 |
| `continue` inside a switch | diagnostic | diagnostic (by name) |

The hang is the one worth remembering: with the depth one level out, a `br` inside
a loop re-entered the loop instead of leaving it, and the test suite did not fail,
it stopped. See the ten tests in `tests/wasm.test.ts` and the skip under "known
gaps".

### BUG-WASM-22 — a fix point that never settled, and the gate it silenced (fixed)

**The corpus gate — the one measurement that says what this backend is worth — did
not finish.** It was killed at 280 s having written nothing, because the report is
written at the end. Every earlier run of it in this session behaved the same way,
and the conclusion drawn from that was "the exception check at each call site made
the scan slow". **That conclusion was wrong**, and it was drawn without measuring
where the time went.

Measuring, per program, with the name announced *before* compiling:

```
      1ms  DIAG     src\cli\commands\dev.no
      8ms  INVALID  src\cli\commands\fmt.no
     73ms  PARSE    src\cli\commands\repl.no
    192ms  INVALID  src\cli\commands\test.no    ← 2.7 minutes later, still going
```

One program. Everything else was 1-92 ms. Splitting that one by phase:

```
parse       8ms
lower       3ms
link       18ms
emit        — never returns
```

Not the lexer, not the parser, not the lowering, and not the exception check. The
**emitter's address inference**, `inferModuleAddressTypes`, which is a fix point:

```ts
while (changed) { … }
```

**A fix point over a set that can move BOTH ways does not terminate.** Two facts
were being learned about the same names, and each overwrote the other:

- `learnKind(name, kind)` wrote `kinds[name] = kind` unconditionally. `kinds` is
  per function, and one function wrote a list of records where another wrote
  numbers, so the two rules set `changed` on alternating passes.
- `fieldElementKind.set(field, kind)` had the same shape, and it is *fed by*
  `kinds` — so fixing one without the other would only have moved the cycle.

Both now only ever **widen**: `number` → `address` is taken, `address` → `number`
is ignored. One order over `{number, address}` and a monotone update means the loop
settles in at most two passes per name.

**The other inference loop in the same file already said this out loud** — "only
ever widen: a pass that narrowed would oscillate" — and this one had the identical
shape without the guard. The lesson is not "add a guard"; it is that **a rule
about non-termination belongs to every loop of that shape, and the one written
down is not automatically the one that has it.**

A pass cap now turns a hang into a sentence, because a fix point that does not
settle is a compiler defect and the honest shape for one is a refusal:

```
los tipos de este módulo no convergen después de 41 pasadas (inferencia de direcciones)
```

**Measured effect on the gate:**

| | before | after |
|---|---|---|
| gate wall clock | killed at 280 s, nothing written | **1.2 s** |
| programs reported | 0 of 50 | 50 of 50 |

```
files 50 · programs 50 · valid 8 · invalid 16 · parse 11 · diagnostics 15 · threw 0
```

The whole point of this entry is that the measurement was unavailable until it was
fixed. **A gate that does not finish is not a slow gate; it is no gate**, and the
cost is invisible precisely because there is no number to look at.

### BUG-WASM-23 — `!` emitted its operand at the wrong type (fixed)

**10 of the 16** modules the engine rejected failed the same way:

```
WebAssembly.Module(): Compiling function #0 failed:
  i32.eqz[0] expected type i32, found local.get of type f64 @+1809
```

`i32.eqz` exists in exactly two places in this emitter: the loop header, and `!`.
The loop header converts its condition explicitly, so the error is `!`.

**The defect was directly below its own correct twin.** The `binop` case above it
carries the rule in a comment:

> Emit operands at THEIR type and choose the opcode from the operator, not from
> the destination local.

and `unaryop`, eleven lines lower, emitted at `local.type`:

```ts
emitValue(inst.argument, ctx, local.type, buf);   // ← the destination's type
emitUnaryOp(inst.operator, local.type, buf);
```

`derive` types a `!` result **from its argument**, so `!x` on a number settles an
`f64` local; the operand went on the stack as a double, and `i32.eqz` wants an
i32. The `local.set` on the next line was wrong for the same reason — a 0/1
result into an f64 slot. Both sides fixed: operand and opcode at i32, and the
0/1 converted to whatever the local actually is.

The corpus is full of `!` — nullish checks, negated calls, empty tests — and the
suite had **no `!` on a number at all**, which is why 838 tests were green over
10 broken modules.

```
files 50 · programs 50 · valid 8 → 11 · invalid 16 → 13
```

**A wrong hypothesis, recorded because the way it was wrong is the point.** The
first attempt was the declared-local mismatch: `ctx.locals[name].type` is settled
by inference, `localTypes[i]` is whatever the slot was *reserved* with, and a
comparison temp settled on `i32` was declared `f64`. Writing the settled types
back **broke 25 of 838 tests**. The reason was an off-by-N in my own arithmetic,
not a wrong idea: `ensure` pushes onto `localTypes` and takes the index from
`ctx.nextLocal`, which is already `fn.params.length`, so `localTypes[k]` is slot
`params.length + k`. Writing `localTypes[slot.index]` shifts every type by the
parameter count — not a wrong type, a **scrambled set** of them, and a function
with four mixed-kind locals then fails for a reason unrelated to the fix. With
the offset done properly the same write-back is harmless and the corpus does not
move, which is what proved the hypothesis wrong: **it was not the cause.**

So two lessons, and the second is the one that would have saved the turn: the
broken fix and the real one had **nothing to do with each other**, and the
25 failures were the only thing that distinguished them from a correct-looking
change.

### BUG-WASM-24 — a function that returns a record in one branch and a number in another (open, and it is a decision, not a patch)

With the `i32.eqz` family gone, **8 of the 13** remaining rejections are one shape:

```
local.set[0] expected type i32, found f64.add of type f64     (5)
local.set[0] expected type i32, found call of type f64        (3)
```

**It is not a type-emission bug.** Localised to one instruction, in
`src/cli/commands/deploy.no`:

```ts
fn loadConfig() {
  const configPath = path.resolve(process.cwd(), 'nodeon.json')
  if !fs.existsSync(configPath) { return {} }        // a RECORD
  try {
    return JSON.parse(fs.readFileSync(configPath, 'utf8'))   // a NUMBER (a host call)
  } catch (e) {
    return {}                                        // a RECORD
  }
}

export async fn runDeploy(args) {
  const config = loadConfig()          // ← the destination is a record: config.deploy.target
```

`loadConfig` returns two kinds. `inferResultType` takes the widest, `f64`, and the
signature says `results=f64`. The caller uses the result as a record, so the module
analysis pins `config` to `i32`, and the body stores the call's `f64` into it with
no conversion. A wasm function has **ONE result type**, so there is no assignment
of `loadConfig` that satisfies both.

**Measured across the corpus:**

```
functions lowered      236
with at least a return 184
return BOTH kinds       9
```

```
build-prod.no :: loadConfig              deploy.no :: loadConfig
db.no :: loadAppliedMigrations           db.no :: discoverMigrations
test.no :: runTestFile
optimizer.no :: optimizeExpression       optimizer.no :: optimizeBinaryExpression
optimizer.no :: optimizeUnaryExpression   optimizer.no :: lowerArrayMethods
```

**9 of 184.** And it is the third time the corpus has said the same thing:

- a list that mixes numbers and records — BUG-WASM known gap, `it.skip`;
- the truthiness of a string, which is the truthiness of its address;
- now a function whose result is a record in one branch and a number in another.

All three are one sentence: **Nodeon is dynamically typed and a wasm slot has one
type.** The escapes are the same in each case and all of them are decisions about
the language rather than about this backend: a tagged cell, a declared result type,
or a `Maybe`/union in the core. Until one of those is chosen, each of these is
counted and named rather than approximated — and approximating it is what produces
a module that validates and computes a truncated pointer.

**Two hypotheses tried and discarded here, recorded because both looked right:**

- *The declared local and the settled local disagree.* Writing the settled types
  back into `localTypes` **broke 25 of 838 tests**; the cause was my own
  arithmetic (`ensure` takes the slot index from a counter already at
  `params.length`, so `localTypes[k]` is slot `params.length + k`). Done correctly
  it breaks nothing **and moves the corpus not at all**, which is what refuted it.
- *`derive` typed every `call` as `f64`.* It did, while `producedKind` ten lines up
  asked the module whether the callee returns an address. Making `derive` ask the

```no
  fn outer(x) {
    fn inner(y) { return y + k }
    return inner(x) * 2
  }
  return outer(n)
}
```

**Four parts, and none of them was the one the diagnosis named.** The first three

three.

1. **A nested `fn` BINDS its own name** in the body it is written in — the same
   treatment a `VariableDeclaration` already got in `collectDeclarations`. The scan
   ran before the name was registered, so `inner` was taken for a free variable of
   `outer` and dragged up with it.

   ```
   before   captures: {"outer":["inner"], "inner":["k"]}
   after    captures: {"inner":["k"]}
   ```

2. **The chain**: a nested function's captures join the ENCLOSING LIFTED function's
   list. Not threadable by scanning — the scan deliberately stops at a nested
   declaration, because a nested body's internals must not leak into the enclosing
   captures. So `outer` cannot discover `k` by looking and has to be **told** by
   `inner`. Alone this is worse than nothing: the call site pushes an argument too
   many for a one-parameter function, and the error names neither the cause nor the
   construct. That intermediate state is why the chain alone was reverted once.

3. **The signature, rebuilt AFTER the body.** A capture has to be a PARAMETER of
   the function that reads it, and a nested `fn` learns its own captures from
   INSIDE `lowerFunction`, long after the parameter list was frozen. A lambda gets
   this free — its captures are computed before the body and prepended.

   a function is *discovered*, and at that moment its own captures are still
   whatever the scan could see — which for a middle function is *nothing*, because
   its capture lives inside the function nested in it. Three levels stopped after
   one hop:

   ```

   after     captures: {"c":["k"], "b":["k"], "a":["k"]}
   4 levels  captures: {"d":["k"], "c":["k"], "b":["k"], "a":["k"]}
   ```

   One line, and it holds at any depth because the unwind is what carries it.

`b(k, x)` reading a local `k` that was not there, and:

**One known cost, measured in four shapes and correct in all four:** a function
that *declares* a name its nested function captures still lists it in `captures`
and takes it as a dead leading parameter. The local always shadows it — including
when the declaration sits in a branch or appears after the reader — so no wrong
answer comes out of it. It is a wasted argument, not a wrong one.

**How this entry was wrong twice.** First the chain was reverted as "wired to
nothing" — a wiring fault mistaken for a wrong idea. Then it was built, fired, and
the answer was still wrong, while a rule I had just written down said to check
wiring *first*. **Both failures exist and the same reasoning cannot tell them
apart; only a measurement that prints the fact and its consumer together can** —
`captures` AND `params`, and the pushed count against the declared count, in one
run.

### BUG-WASM-36 — a class is a record plus a table of lifted functions (closed)

**The gate went DOWN with this one: `valid 7 -> 3`, and every one of those four
programs was compiling while its `new Set()` was silently dropped as a zero.**

  ```
  src/cli/utils/strings.no       new Set(): 0     Array(): 1
  src/language/keywords.no       new Set(): 1
  src/language/operators.no      new Set(): 4
  src/language/precedence.no     new Set(): 1
  src/language/symbols.no        new Set(): 1
  ```

There was no `NewExpression` case at all, so `new` fell through to the branch that
emits a placeholder comment and carries on. A program that built its whole data
structure with `new Set()` produced a valid module that answered 0. Naming it cost
four green programs and bought the truth. `new Array()` came back immediately — a
list of zeros is not waiting on any decision — and one of the four returned.

**The other four are `new Set()`, and that is blocked on a question only the
language's author can answer: whether a string here is a BYTE string or a CHARACTER
string.** It is worth four of the seven programs the backend could compile.

---

**What was measured before anything was designed** (`.mavis-probe/classes.txt`):

  18 classes · 160 methods · 12 files · inheritance 5 deep
  `this`      an ordinary Identifier, 1118 uses, never a `ThisExpression`
  `super(…)`  5 calls, all in constructors — and `super.m(…)`: ZERO
  members     `ClassMethod` and `ClassField`; `body` IS the array, not `body.body`

That last line is a bug I wrote: the first inventory read the class body as ESTree
and reported **0 members on all 18 classes** while the source plainly has
constructors. Nodeon's AST is its own shape. A measurement that contradicts the file
it is measuring is measuring the wrong thing, and the tell was that it contradicted
something anyone could read.

**The design needed nothing new in the emitter.** A class instance is a record, and
each method is a lifted function whose FIRST WRITTEN parameter — after the captures,
which the emitter already pushes itself — is the receiver. So:

  `this.x`   a `loadfield` on an ordinary ref
  `this.m(…)` and `c.m(…)`   an ordinary `call`
  `new C(…)` an `objlit` followed by a call to the constructor

and the receiver is typed as an **address** by a rule the emitter already had:
`receiverParamNames` — *a parameter used as the receiver of a field access IS a
record*. The receiver is exactly that, so nothing said so.

**Inheritance is a COPIED method table, not a chain.** A subclass starts from its
parent's methods and overrides what it declares. The only thing left to do at run
time is `super(…)`, which runs the parent constructor on the same record — and with
no `super.m(…)` anywhere in the corpus, that is the whole of it. Five deep works:
`Parser` → `ParserStatements` → `ParserExpressions` → `ParserTypes` → `ParserBase`.

---

**Two defects, and both were found by running the thing and reading the NUMBER.**

1. **The class registry lived on the wrong object.** `lowerToIR` builds a fresh
   `BlockBuilder` for every top-level statement, so the registration `class A` made
   was gone before `B` was lowered:

   ```
   class A { who() { return 1 } }
   class B extends A { who() { return 2 } }
   -> la clase "B" extiende de "A", que no es una clase de este módulo
   ```

   A is two lines above B, in the same file. A module-wide fact was being created by
   a per-statement builder — the same shape as `captures` and `functionNames`, and
   the same fix: make it once in `lowerToIR` and thread it through. It then had a
   *second* consumer to reach, the top-level `lowerFunction` call, which was still
   handing every function body a fresh empty map.

2. **`new` returned the CONSTRUCTOR'S RESULT.** A constructor has no `return`, so
   its result is whatever is in the result slot — zero — and `new` handed THAT to the
   binding. Every method call went through address 0:

   ```
   let c = new Counter(s)   // want n = 1
   c.add(4)                 // want n = 5
   return c.add(6)          // want 11
   got 10                              which is 4 + 6
   ```

   All nine cases compiled and seven answered a wrong number. The valid-module-
   wrong-arithmetic shape, and the only reason it was caught is that the probe
   printed the ANSWER instead of a verdict. **A test that asserts a module builds is
   a test this bug passes.**

---

**And the refusal that was already there was hiding a second one.** Six programs
failed to LINK, not to compile: `parser.no importa "ParserStatements" y
src_compiler_parser_parser_statements no lo exporta`. Six files, one cause — the
linker registers a file's exports by looking for `FunctionDeclaration` and
`VariableDeclaration`, and a class is neither. **The class gap was not 13 programs,
it was 19**, because it also made six classes un-importable.

Ten tests cover this: the field, the method, a method calling a method, a class field,
`super()`, an inherited method, an override, three-deep constructors, a record in a
field, a method that returns nothing, and `new Array()`.

**What is still not resolved, and is named rather than guessed:** a method call on a
receiver that is neither `this` nor a binding that received a `new` — a value out of
a function, say. The emitter refuses it by name. Making that work is a vtable, and
this backend has no need for one yet.

### BUG-WASM-37 — `new Error(…)` is a record; and there is no string type

**Measured before it was built, because the shape decided the size of it:**

  18  throw new Error(…)
   0  bound to a name, returned, or read

Every one of the eighteen is a value constructed only to be thrown. So the honest
shape is a record with `message` and `name`, built with the same `objlit` a class
instance uses. `SyntaxError` and `TypeError` are the same record with their own
name.

**There is deliberately no `stack` field.** There is no call stack to read in a
WebAssembly module, and a `stack` that comes back as zero is worse than an absent
one: the program prints a trace with nothing in it and nobody can tell it from a
real one.

**A test that reads the value caught a hole the build-only test could not.**
`fieldIsAddress` is learned from the NAMES of the values an `objlit` stores, and
`valueName` returns null for a literal because a literal has no name. So a field
written from a string literal was never learned as an address field and became an
f64 slot holding a pointer:

  ```
  throw new Error("negativo: " + n)   catch (e) { return e.message }
  got 4, want "negativo: -4"                 4 is the address
  ```

**That is not an `Error` bug.** Every record literal in the language that stores a
string hits it: `{ msg: "hola" }` writes a pointer into a slot the reader loads
as a double. A string literal IS an address, so the field holding one is an
address field whether or not anything has a name.

---

**And the honest answer to `got 4` is the real finding of this stretch: this
backend has no string type.** Measured:

  ```
  return "hola"                    → 8    the address
  o = { m: "hola" }; return o.m    → 8    the address
  a == b   (two equal strings)     → 1    ✓ string equality works
  "hola" + " mundo" → .length      → 0    ✗ concatenation does not exist
  ```

A function's result is **f64** and a string is an **i32 address**, so a string that
goes into a function comes out as its address. `+` between two strings is not
concatenation, and `.length` on the result is zero.

**This is bigger than the collections question, and it sits underneath it.** Almost
every refusal in the corpus is downstream of it: `throw new Error("file not found: "
+ inputPath)`, `entry + "  if (pathname.startsWith…`, a `Set` of names. The
byte-or-character decision decides what a string IS; this decides whether there is
a string at all, and it is the bigger half.

A test asserts the gap rather than the behaviour, so it stays visible:

  ```ts
  it("a string cannot be RETURNED yet — the result type is f64", () => {
    const got = instantiate(src, "run")();
    expect(typeof got).toBe("number");   // the address, not the text
    expect(got).not.toBe(0);
  });
  ```

**It asserts the TYPE and not the value on purpose.** The address is 8 today and
will be something else the day the heap moves, and a test that pinned 8 would then
fail for a reason that is not a defect. What must not change is that it is a
number and not a string — that is the false number, and a test that lets it pass
unnoticed is how it ships.

---

**Two things measured in the same pass that are worth not rediscovering:**

- **`Object.assign` is not implementable as a helper.** All five uses in the corpus
  have their SOURCE keys as runtime values — `Object.assign({}, sandbox)`,
  `Object.assign({}, constants)`. Copying an arbitrary record's fields needs the
  field set at run time, and a record's shape here is fixed at compile time with
  module-wide offsets. It is three programs (`fmt.no`, `run.no`, `start.no`) and it
  is a dynamic-object feature, not a helper.

- **The biggest single blocker left is the LINKER, not the backend.** Six files
  fail with `importa "NodeonError" y src_compiler_errors no lo exporta`, and it
  reaches nine programs once `compile.no`, `repl.no` and `cli/index.no` are
  counted. `linkProgram` registers a file's exports by looking for
  `FunctionDeclaration` and `VariableDeclaration`; a class is neither. The class
  gap in BUG-WASM-36 was therefore **19 programs, not 13** — and only the half of
  it that is a backend refusal is fixed. It needs more than registering the name:
  `linkProgram` lowers each file with its own `lowerToIR`, so a class in
  `errors.no` is invisible to the `new NodeonError()` in `parser-base.no`, and the
  class's lifted functions have to become reachable through the import or the
  rename will not match them.

### BUG-WASM-38 — a `Set` is a list of addresses, and the write is the wrong width (closed by BUG-WASM-42)

> **Superseded in part by BUG-WASM-39**, which closed the width half: an array
> literal of strings is typed `address` now and the elements land correctly. The `Set`
> is still reverted, because its `has` is the scan that BUG-WASM-39 measured as still
> broken — and a set whose contents are right and whose only operation cannot find them
> is still a false capability.

**The byte-or-character question is NOT on this path, and that is worth knowing.**
A set of string addresses compares addresses: `has` and `add` never look at what
is inside a string. So they are the same instructions whichever way that question
is answered, and the four corpus files blocked by `new Set()` can stop waiting for
it. The corpus asks for:

  new Set(["fn", "if", …])   keywords.no, operators.no, precedence.no, symbols.no
  .has   9 in lexer.no, 21 in type-checker.no
  .add   2, .forEach 2

**A first measurement of that got it wrong in a way worth recording.** Searching each
file on its own found **zero** set operations in all four — they build a set and
export it, and the *lexer* asks the question from another file. A per-file
measurement of a value that crosses a file boundary finds nothing, and reports it as
an absence rather than as a limit of the search.

---

**The representation was a list of addresses** — which makes `has` a scan comparing
addresses and `add` a scan plus a push, both written in the language itself the way
the list helpers are. It got the gate from `valid 3` to **`valid 7`**, with no
regression in 878 tests.

**And it was wrong. The gate was measuring the wrong thing:**

  ```
  new Set(["fn", "class"]).length      → 2   ✓
  new Set(["fn", "class"]).has("class") → 0   ✗
  S = new Set([]); S.add("fn"); S.add("class"); S.has("class") → 1   ✓
  ```

Same two values, same helper, same comparison. The only difference is how the
elements got there — `storeelement` against `push` — and the length is right while
the content is not. The length is a HEADER the array literal writes itself; the
elements are written afterwards, one at a time. **So the write is wrong and the
reader is the same reader in both cases.**

This is the same hole `fieldIsAddress` had for literals (BUG-WASM-37), on the array
path instead of the record path: a value that is an ADDRESS is being written at
f64 width into a slot the reader loads as i32. The repo already knows the array side
of this — `it.skip("a list that mixes numbers and records")` is the same defect seen
from the other end.

---

**So it was reverted, and this is the part of the entry I would keep.**

Four programs — `keywords.no`, `operators.no`, `precedence.no`, `symbols.no` — went
green, and the gate said 7, and the number was **still wrong**. Each of those four
compiles correctly: everything in them works, they build a set of the right size.
What is corrupt is what they EXPORT, and the corruption only shows up in the file
that consumes it — the lexer, which is still refused for other reasons, so nothing
in the corpus ever exercised the broken path and the gate had no way to see it.

**A green gate is not evidence that the feature works; it is evidence that the
program the gate ran did not notice.** Those four files build a collection and hand
it to somebody, and the somebody was not in the measurement. A gate that counts a
program as good because it COMPILES is measuring the compiler, not the language —
and a compiler that writes a wrong value happily is exactly what this project has
spent its whole buglist refusing to ship.

The rule that came out of it, and it is the same one as everywhere else here:

- **Land a data structure on a test that READS it back, not on one that builds it.**
  Every class test and every error test that failed in this stretch failed exactly
  there — `got 4` where a string should be, `got 10` where 11 should be. A
  build-only assertion passed every one of those bugs.
- **A value that crosses a file boundary is not measured by searching one file.**
  The set that looked unused was the most used thing in the language.
### BUG-WASM-39 — an array literal of strings was typed `number` (closed)

**Three defects, one cause, and this is the third.** A value that is an ADDRESS,
written where the width has to be i32:

  BUG-WASM-37   a record FIELD written from a string literal
  BUG-WASM-38   a set ELEMENT written by `storeelement`
  BUG-WASM-39   an ARRAY ELEMENT in a literal           ← this one

The first two were found by reading a value back. This one was found by asking a
question the gate never asked — *what does the lowering think this list holds?* — and
the answer was in the same output as the wrong number:

  ```
  const L = ["fn", "class"]
  arrayKinds: {"L":"number", "_t0":"number"}      ← numbers, and they are not
  L[0]               → 0          the literal that was pushed, not the address
  L.length           → 2          the header is a separate write and was right
  L.indexOf("class") → -1         the element is there

  const L = [10, 20]
  L[1]               → 20         ✓ a numeric literal is fine
  ```

**`ArrayExpression` decided "all numbers", and the only rule that ever turned that
off was an OBJECT element.** A string literal fell through the `else`, its address
went into a number slot as a double, and the scan that read it back never matched.
One line of recognition was missing:

  ```ts
  if (el?.type === "Literal" && typeof el.value === "string") { allNumbers = false; … }
  ```

**`indexOf` returning −1 for an element that IS in the list is the worst shape this
backend produces.** Not a crash, not a zero: a confident wrong answer that reads as
an empty result, from a function whose only job is to say whether something is
present. A program that checked membership would have carried on with the wrong
world and nothing downstream would have looked odd.

---

**What is fixed and what is not, because they are different defects.**

Fixed, and measured on the value rather than on the build:

  const L = ["hola"]            L[0] is the address, not 0
  const L = ["hola", "mundo"]    L[1] is the address, not 0
  const L = [10, 20]             L[1] is still 20
  const L = [1, 2]               L[0] + L[1] is still 3

**Still open, and it is NOT this bug:** a scan over a list of addresses finds the
element in a ONE-element list and returns −1 for every element of a two-element one,
with both slots holding the right addresses. The data is right and the SCAN is
wrong. It is `it.skip` in `wasm.test.ts` with the measurement next to it, because the
header of that file says a skip marks a known gap WITH the reason, and a permanently
red suite is not that — it is a suite nobody can read.

**This is also why the `Set` of BUG-WASM-38 was reverted at the time** — its `has` is that scan.
A Set whose contents are now correct and whose only operation cannot find them is
still a false capability, and the second time measuring it bought exactly this: the
typing hole and the scan defect are separate, and only one of them is a one-liner.

### BUG-WASM-40 — the same program gives two different answers depending on order (closed)

```
  npx vitest run tests/wasm.test.ts -t "finds a string in slot 1"
    1 passed
  npx vitest run tests/wasm.test.ts
    1 failed — expected -1 to be 1
```

**The same program. Only which tests ran before it differs.**

---

**How it surfaced, because the road to it is the useful part.** A scan over a list of
string addresses found the element in a one-element list and returned −1 for every
element of a two-element one, while `L[0]` and `L[1]` read back as the right
addresses in the caller's own code. The data was right and the SCAN was wrong —
BUG-WASM-39 is the entry for that.

Then the scan was separated into its three parts, and **all three worked** written in
the caller's own code: a plain loop counting to n, the same returning from inside the
loop, a loop over a two-element address list counting non-zero reads, and both
`list[i] == local` comparisons. The only thing the failing one goes through is a
**lifted helper**.

**And the emitter already knew.** `receiverOperand` reads a `receiverFirst` flag to
decide that a parameter holds a record, and its comment describes this failure almost
word for word. The flag was on the `Math` call site and not on the list one. Setting
it made the program answer 1 when it ran **alone** and −1 inside the **file**.

---

**The first hypothesis was wrong, and that is the part worth keeping.**

Two modules shared one `IRFunction` object, and the emitter types a helper's receiver
per module — so one IR node emitted under several typings, and the answer depended on
which module was compiled first. That is a good story. **It was measured and it was
false:** copying the IR per module did not change the result. The test still answered
−1 inside the file.

**The copy was reverted rather than kept**, because a change whose stated reason has
been disproven is a change nobody can trust later.

**What it pointed at instead is the actual cause.** `lowerFunction` merges the helper
builder's `arrays` into the `arrayKinds` of the module that BUILT it:

```ts
Object.assign(arrayKinds, Object.fromEntries(b.arrays));
```

so a helper's temporaries are registered as lists in module 1's `arrayKinds` and in
nobody else's. A module reusing a cached helper got the **instructions** and not the
**table saying how to read them**. `list.length` and `list[i]` then lowered at the
wrong width and the scan missed.

**The IR is a contract, and the tables that say how to read it are part of that
contract. A cache that ships one without the other ships half a fact.**

The cross-module cache is gone. `b.helpers` already dedupes within a module, so no
program builds a helper twice; what is paid is one parse and one lowering per MODULE
that uses the method. The cache existed to avoid exactly that, and what it bought was
a program whose answer depended on what had been compiled before it.

Measured after: **188 passed in the full file, 0 failed**, with the test that failed
before now a real assertion. No `receiverFirst` anywhere.

---

**What it cost to find, stated so it is not paid twice:**

- **A green suite is a statement about the ORDER it ran in.** A test that passes alone
  and fails in its file is not a flaky result to re-run — it is the answer, and it was
  available from one extra command.
- **A plausible mechanism is not a cause.** The shared-object story was tidy, it
  matched the symptoms, and it was wrong. The measurement that killed it is what
  found the real one; keeping it would have cost the same hour and shipped a lie.
- **When a cache ships a computed thing, ask what ELSE travels with it.** The IR was
  the thing being cached and the `arrayKinds` entries were the thing that mattered.

**And the slot-0 gap closed with the same fix — which I had not checked.**

The entry above said the scan still missed slot 0 and that this was the last thing
between the fix and the `Set`. **That was a claim about an `it.skip` that had not
been run against the fixed code**, and it was wrong:

```
  vitest run tests/wasm.test.ts -t "…SLOT 0"    1 passed
  vitest run tests/wasm.test.ts                 189 passed, 0 failed
```

Both. Removing the cross-module cache fixed the first element and the second. The skip
had been written when the code was broken and nothing had gone back to read it — the
same failure the project has already paid for three times in this file, and the
cheapest one to avoid:

- **A skip is a claim about the code, and it expires the day the code changes.** It is
  not a marker, it is an assertion nobody has re-checked.
- **The one command that finds this is running the skipped test.**

**So the scan over a list of addresses works in both slots, and the `Set` is not
blocked by that any more.** It is blocked by the next thing, which is sharper:

  ```
  S = new Set([]); S.add("fn"); S.add("class"); S.has("class")   → 0   ✗
  S = new Set([]); S.add("a");  S.add("a");    S.has("a")       → 1   ✓
  ```

**`push` on a helper's list parameter grows the array once and not twice.** The second
test only ever reaches one element — the scan finds the value after the first push
and the rest are no-ops — so it looks correct and never exercises a second push.
That is a capability whose passing test does not reach the failing line, and it is
the third time in this stretch that a test which passes is not a test of the thing
it is named after.

### BUG-WASM-41 — RETRACTED: the capacity-0 diagnosis was false

**This entry was written twice. The first version claimed a defect that does not
exist, and it is retracted here rather than deleted, because a retraction with its
evidence is worth more than a silent removal.**

**What it claimed:** the array header is two words —

```
  base + 0   length
  base + 4   capacity
```

— and `push` grows with `newCap = cap * 2`, so **doubling zero is zero** and an
empty array could never grow. The symptom it was built to explain:

```
  S = new Set([]); S.add("fn"); S.add("class"); S.has("class")   → 0   ✗
  S = new Set([]); S.add("a");  S.add("a");    S.has("a")       → 1   ✓
```

**What is actually true:**

```ts
/** Capacity an array literal is created with: length rounded up, minimum 8. */
function arrayCapacity(length: number): number {
  let cap = 8;
  while (cap < length) cap *= 2;
  return cap;
}
```

`arrayCapacity(0)` is **8**. Every array literal is created with capacity 8 or more,
the growth path always moves, and **the floor could never fire**. The first fix was
dead code.

**And it broke three tests anyway**, which is the part that says something:

```
  keeps every element across several growths   expected 780, got 776
  grows past the memory the module was given   failed
  the same answers as the JS backend           wasm 0, reference 3
```

Dead code does not break anything. So the edit changed something it was not meant
to — most likely the extra `ctx.scratchLocal()` shifting the local numbering, or a
misplaced `else`-branch instruction. **A change that alters behaviour while its own
justification provably cannot apply is a sign the model is wrong, not that the
change is delicate.** The revert was right and the diagnosis was not.

---

**The `push` path was measured next, and it is fine too:**

```
  const L = []; L.push("hola"); L.push("mundo")   L[1]  → 16  ✓
  … the same                                      L[0]  → 8   ✓
  … two numbers                                   L[1]  → 22  ✓
  … indexOf("mundo") on two pushed strings               → 1   ✓
  … three distinct pushes                        length → 3   ✓
```

**And that measurement carries the next real observation.** The list of pushed
strings is typed `{"L":"number"}` — the WRONG kind, since a string is an address —
and it works anyway, because the width is then consistent between the store and
the load. **Every defect in this family has the same shape: a slot written at one
width and read at another.** A consistent mistake does not misbehave; an
inconsistent one does.

---

**What is actually still open, stated as narrowly as the evidence allows:**

```
  new Set(["a", "b"]).has("b")            works
  new Set([]); S.add("a"); S.add("b")     S.has("b")   → 0
```

A list built by a **literal** is answerable and a list built by **`add`** is not, and
the two differ only in how the elements were written. The `add` and `has` helpers are
lifted with their receiver seeded as an ADDRESS, while a literal-built list's kind is
learned from its `arraylit`. **So the next thing to measure is whether the receiver's
seeded width and the list's learned width ever disagree** — and if they do, that is
the same class as BUG-WASM-37/38/39, one level up: a value written at a width nobody
reading it agrees on.

**Three things this retraction is worth, independent of the `Set`:**

- **A symptom is not a cause.** `add` twice failing and `add` three times the same
  value passing is a real fact, and I built a heap-allocation story on it that turned
  out to be about a function whose first line is `let cap = 8`.
- **Check the constant before theorising about the arithmetic.** `arrayCapacity` was
  four lines away from the code I spent the reasoning on.
- **Dead code that changes behaviour is the loudest possible signal that the model is
  wrong.** It was not delicate; it was wrong, and three tests said so immediately.

### BUG-WASM-42 — `push` wrote f64 into a slot the reader loaded as i32 (closed)

```ts
function emitStoreAtIndex(ctx, buf, baseLocal, lenLocal, value) {
  …
  emitValue(value, ctx, "f64", buf);
  buf.push(OP.f64_store);
}
```

The READ of the same slot asks the list's element kind. So a list of ADDRESSES was
written as a double and read as an i32, and the reader saw the low 32 bits of a
double — which, for an address in this heap, is **ZERO**, because the address is the
whole mantissa. Every element came back 0 and the scan found nothing.

**The rule already existed and `push` never asked.** `storeelement` — the write an
array LITERAL makes — does exactly this:

```ts
const isAddressArray = isAddressArrayValue(ctx, inst.array);
if (isAddressArray) { emitValue(value, "i32"); i32_store } else { … f64 … }
```

**One writer had the rule and the other hardcoded an answer.** That is the whole
family:

  BUG-WASM-37   a record FIELD written from a string literal
  BUG-WASM-38   a set ELEMENT written by `storeelement`
  BUG-WASM-39   an ARRAY ELEMENT in a literal
  BUG-WASM-42   an ARRAY ELEMENT written by `push`        ← this one

---

**The measurement that found it, and why two earlier ones did not.** The two cases
are the same code differing only in the list's kind:

```
  const L = []; L.push("hola"); L.push("mundo")     arrayKinds {"L":"number"}
  L[1]                                                       → 16   ✓

  const S = new Set([]); S.add("fn"); S.add("class")  arrayKinds {"S":"address"}
  S.has("class")                                            → 0    ✗
```

**A consistent mistake does not misbehave; an inconsistent one does.** The first list
is typed `number` — the WRONG kind, a string is an address — and it works, because the
wrong width is used on both sides. Every bug in this family is a slot written at one
width and read at another, and no amount of looking at a case that happens to be
self-consistent will find it.

---

**Two false diagnoses came first, and both are in this file because they cost the
most.**

1. **A capacity-0 heap bug** (BUG-WASM-41, now RETRACTED). `push` grows with `cap * 2`
   and doubling zero is zero, so — I wrote — an empty array could never grow. The
   first line of the function that decides it is `let cap = 8`. A floor was added, it
   was dead code, and it broke three tests: the loudest possible signal that the model
   was wrong.
2. **Then `push` itself was exonerated** by six passing cases — and those cases were
   all lists typed `number`, so they exercised the consistent case and proved nothing
   about the inconsistent one. **A test that only covers the case that works is a test
   of nothing**, and it was written to exonerate a function.

**What actually located it was a prediction, not a search.** After the second false
diagnosis the rule was stated once — *a slot written at one width and read at another*
— and the next thing to read was the one writer that did not consult the rule. It was
four lines long and had been there the whole time.

---

**The Set lands with this, and it is the fourth time the gate said 7.** The previous
three were wrong: the four programs that came back only BUILD a set and export it, the
consumer — the lexer — is still refused for another reason, and so **nothing in the
corpus ever asked the set a question.** The gate was measuring the compiler, not the
language. This time the tests ask the question the gate could not, and the one that
matters is the shape that was missing four times over:

```
  S.add("fn"); S.add("class"); S.has("class")   → 1   ✓
  S.add("a");  S.add("a");    S.has("a")        → 1   ✓
```

Adding the SAME value three times passes on a Set whose `add` never grows it — the
scan finds the value and the rest are no-ops. **Two different values is the first
shape that reaches a second push.**

**`has` and `add` do not depend on whether a string is bytes or characters.** They
compare addresses and never look inside a string, so the open decision does not gate
them. The decision is about `slice` and `length`, and it is still the user's.

Still open, and named: a Set **handed back from a function** does not survive, because
a function's result is f64 and a list is an i32 address. Same gap as returning a
string, same fix, and it is the largest thing left in the backend.

### BUG-WASM-45 — a module-level `const` bound to a record reads back 0 (open)

The three type-only declarations stay: they emit nothing, so they cannot be wrong.

---

**What is affected, and it is not small.** Any `const X = { … }` at module level, and
any `const X = [ … ]` whose reads go through a field. The corpus has
`export const DELIMITERS = new Set([…])` and `export const KEYWORDS = new Set([…])`,
which are read through a METHOD (`KEYWORDS.has(…)`) rather than a field — so the one
shape the corpus happens to use works, and the shape it does not use is the one that

**That is the third time in this stretch, and it is worth naming as a pattern.**

  BUG-WASM-37   a record FIELD written from a string literal
  BUG-WASM-42   an array ELEMENT written by `push`
  BUG-WASM-45   a module-level BINDING never materialised at all

Each was found by writing the same thing twice and comparing — a `Set` built by a
literal against one built by `add`, an `interface` alone against one beside a typed
class field, an enum against a plain `const`. **A control has one value and a defect
has none; a single example cannot tell them apart.**

---

**The fix, and why it is not a patch.** A getter that rebuilds a pure value is safe:
`objlit` and `arraylit` have no side effects and no dependencies, so moving them into
a function changes when they run and nothing else. A `call` is not safe — hoisting it
would move a computation to the first use, which is a different program — and that is
presumably the distinction the current code is drawing, except the current code draws
it at *literal versus not* and so strands every record and every list.

So: hoist a `const` whose value is a temp produced by a PURE instruction, and report a
`const` initialised by a call with a name in it rather than letting it read as 0.

**Two things to check before trying, and they are the same two as BUG-WASM-41:**

1. Whether the getter has to be built per NAME or whether one function can return any
   of them — the same shape as the list-method helpers, where the name is the key.
2. Whether a record that is large enough to be a `list` is cheaper to rebuild per read
   than to store once. A getter re-runs its `arraylit` on every call, so a module-level
   list read in a loop would allocate per iteration — and `examples/life.no` and the
   lexer's delimiter table are exactly that shape.

**That second point is why this is not a one-liner even though the fix looks like one,**
and it is the kind of thing that turns into a heap problem later if nobody looked.

---

**What landed while the fix is open: the 0 became a NAMED refusal.**

```

  no se eleva: se leería como 0. Elevar un valor puro es lo que falta; ver buglist.md.
```

**That costs four green programs and buys the truth**, which is the trade this file has
made every time:

  keywords.no     KEYWORDS         new Set([…])   →  a Set of the right size, read as 0

  operators.no    OPERATORS                        →  the same

**Each of those four compiles, exports the collection, and the gate counted it green.**
A program that hands its consumer a `Set` whose contents are zero is not a program that
works, and the reason it went unnoticed is the same as BUG-WASM-43: **the consumer is
the lexer, which is refused for other reasons, so nothing in the corpus ever asked the

**The first version of the refusal was too wide, and the measurement said so.** Reported

twelve of those were

which is a HOST IMPORT, and the emitter already refuses that with a better name: *no hay
host al que preguntar*. **Pointing at a host import as "a constant that is not a

getter a literal already uses, with the CONSTRUCTION as the body instead of a literal:

```

```

gate went to `valid 7` with no regression. Then the values were read:

```

  const S = new Set(["a", "b"])        S.has("b")  → 0   ✗
  const S = new Set(["a", "b"])        S.has("a")  → 0   ✗
  const S = new Set(["a","b","c"])    S.has("b")  → 0   ✗
```

**With a second `storeelement`, NEITHER element is findable.** The body is identical
in shape in every one of those, and `KEYWORDS` has about forty members — so this would
have been a third green gate over a feature that answers zero.

**So it is reverted and the question is written down instead of guessed at:** why does
a `storeelement` land at index 0 and not at index 1, inside a lifted function whose
body is a correct copy of the instructions it replaced?

**One of the six probe cases was worthless and it is worth knowing which.** A module
level Set was asked `has("while")`, whose correct answer is **0** — so it passed whether
or not the set worked. A test whose expected answer equals the answer of a broken
implementation is a test of nothing, and it was written that way by accident while
checking something else. The case that caught this asked a question whose answer is 1.

---

**And the fault is the GETTER, and nothing else. Three variables, separated:**

```
  a list of two numbers, slot 1, inside a function     → 20   ✓
  a Set of two members, has("b"), inside a function     → 1    ✓
  a record of two fields, inside a function            → 12   ✓
  a list of two strings, compared to itself, in a fn   → 1    ✓
```

**So `storeelement` is fine, `has` is fine, and two members are fine.** Every one of
those works in every combination — a record with two fields, which writes its own
fields with no `storeelement` at all, passes, and a Set with two members, which needs
one `storeelement` per element, passes. **The only thing that fails is the same code
inside a lifted function whose body is a byte-for-byte copy of the instructions it
replaced.**

That is a much smaller question than the one this entry started with, and it is worth
stating exactly: **what does a lifted function do differently from a top-level one, for
a body that is a correct copy?** The candidates are all local to the emitter — the
per-function `defs` map, `inferLocals`, the result type the getter's `return` infers, or
a temp NAME that the module-wide `arrayKinds` keys on and that the copied body reuses.
**The last one is the one to check first**: the getter reuses the temp names of the
instructions it copies, and `arrayKinds` is keyed by NAME for the whole module, so a
name the original globals also used could be read with the wrong element kind — and a
body with one element and a body with two have different names in play.

### BUG-WASM-47 — `+` adds two string ADDRESSES, and `.length` reads garbage (open)

**With the gate finally counting, the corpus asks for 132 distinct things, and the
single biggest cluster is strings — about 75 of them, with `path` (45) standing on
top of it.**

```
   11  replace      10  includes    10  split     8  repeat    7  match
    7  padStart      7  trim         4  endsWith   3  slice     2  toLowerCase
    2  toUpperCase    2  charCodeAt
```

---

**Measured, and it is worse than "not supported":**

```
  2 + 3                     → 5              ✓
  "ho" + "la"               → 24             = 8 + 16 — the two ADDRESSES
  "hola".length             → 1634496360     garbage
```

**`+` does not refuse a string. It ADDS it.** Two addresses sum to a number that is
not an address, and every later use of that value is a wrong number rather than a
gap in a list — which is the shape this file has refused all along.

---

**And the fact that decides the design.** A string is interned like this:

```ts
intern(value: string): number {
  const address = this.align(8);
  for (const byte of new TextEncoder().encode(value)) this.buf.push(byte);
  this.buf.push(0); // NUL terminator
}
```

**NUL-terminated and with NO length header.** That is the whole of it:

- **`.length` cannot be a load**, because there is no length to load. It would have to
  be a scan for the NUL, which is why it is a field read today and returns whatever
  eight bytes happen to be there.
- **A concatenation has nothing to copy into**, because nothing knows how long
  anything is.
- **`path` — 45 gaps of pure string manipulation — is built on all of it.** `join` 16,
  `resolve` 10, `dirname` 7, `basename` 6, `relative` 6. No I/O, no operating system,
  just text. It is implementable in the language the way the list methods are, **and
  it cannot be written until this is.**

---

**Three pieces, in this order, and the first is the one nothing else can skip:**

1. **A `stringNames` fact for the module.** `addressNames` already tracks which values
   are addresses — strings, arrays and records are all i32 — and that is exactly why
   `+` cannot tell them apart. A string is a fourth thing, learned from a `literal`
   whose `litType` is `string` and propagated the way the others are. **Until the
   emitter can say which operand is a string, nothing about strings can be right.**
2. **`+` concatenates when either side is a string.** Which needs a runtime helper:
   allocate, copy both, terminate. This backend has no runtime to call, so it is the
   same kind of piece as `emitArrayPush` — real bytecode written here.
3. **Give a string the header an array already has.** `[len: i32][cap: i32][bytes…][NUL]`
   costs four bytes per literal and makes `.length` an `i32.load` instead of a scan,
   and gives a concatenation somewhere to put its result with the capacity already
   known. **`internArray` is the shape to copy, and it is four lines above.**

**And note what is NOT in the decision.** Concatenation does not care whether a
character is a byte. Neither do `split`, `trim`, `toLowerCase`, `replace` or `includes`
as *operations*. The byte-or-character question is about `slice`, `length` as a
CHARACTER count, and indexing — and with the header in (3), `length` is a count of
whatever the header counts. **So most of the string layer can be built before that
question is answered**, and this entry is the work that does it.

---

**What the honest gate now says, for contrast with what it said before:**

```
   27  new Map()          16  join          14  log          12  existsSync
   12  exit               11  error         11  replace       10  cwd
   10  includes          10  readFileSync  10  resolve       10  split
   10  stringify         10  writeFileSync   9  parse         8  assign
    8  mkdirSync          8  repeat         7  dirname        7  match
    7  padStart           7  readdirSync    7  trim           6  basename
```

**The three blocks are strings (~75), `path` (45, on top of them) and the host I/O**
(`fs`, `console`, `process` — `readFileSync`, `writeFileSync`, `existsSync`, `log`,
`exit`, `cwd` — around fifty).** The first two are pure text and buildable in the
language. The third is the one that genuinely needs a host, and it is a design
question rather than a mechanism: a WebAssembly module cannot read a file by itself,
so it needs imports and a host that provides them. **That is the piece where the
backend stops being a compiler and starts being a runtime, and it deserves a
decision of its own rather than arriving as a side effect of a gap list.**

### BUG-WASM-48 — a string has a length header, and `.length` works BY LAYOUT (part closed)

**A string was interned as bytes and a NUL:**

```ts
for (const byte of new TextEncoder().encode(value)) this.buf.push(byte);
this.buf.push(0); // NUL terminator
```

so `.length` had nothing to load — it would have had to scan for the NUL — and
became a field read of the record layout instead. Measured: `"hola".length` returned
**1634496360**, whatever eight bytes happened to be there.

**It is now `[len: i32][cap: i32][bytes…][NUL]`, the same two words `internArray`
already wrote four lines below.** Eight bytes per literal, the NUL kept so anything
that walks to a terminator still works, and `.length` on a string in a local returns
4.

---

**And the part worth writing down is HOW it works, because it is not what it looks
like.**

```
  let s = "hola"; s.length   →  {"op":"arraylength","array":{"kind":"ref","name":"s"}}   → 4   ✓
  "hola".length               →  {"op":"loadfield","field":"length"}                     → denormal ✗
  { length: 99 }.length       →  {"op":"arraylength","array":{…}}                         → 0    ✗
```

**`.length` lowers to `arraylength` on a NAME** — the same rule every list method uses
— and `arraylength` reads offset 0, which is where the new header puts the length and
where an array header already put it. **So it is right by LAYOUT, not because the
emitter knows `s` is a string.** The emitter does not: `addressNames` says a value
holds an i32, and strings, lists and records are ALL i32.

**A coincidence that is also a convention, and it has two edges, both measured.**

1. **A string LITERAL's length does not work.** `"hola".length` takes a different
   route — `loadfield` instead of `arraylength`, a different instruction reading an f64
   where the header holds an i32 — and answers `8.48e-314`. `it.skip`, with it.
2. **A record with a field called `length` is unreadable**, and answers 0. **That one
   is not new and not caused by the header**: `.length` has always been a name-based
   rule, and such a record has always been swallowed by it. It is named here because
   the same rule is what makes the working case work, and a rule that is right for
   lists and strings and wrong for records needs the thing BUG-WASM-47 asked for —
   **a module-wide way to say what a value holds.**

---

**The order was the reverse of the one first written, and that is the part to keep.**
The design in BUG-WASM-47 listed the header third, behind `stringNames` and behind
`+`. **The header is first**, because a concatenation cannot be written until there
is a length to allocate against, and because once the length is at offset 0 the
commonest operation started working without either of the other two. Reading a design
as a list of steps and building it in that order is how a prerequisite ends up
last.

**And it is a test that counted.** One assertion, `"añb".length` = 4, says the header
counts BYTES and not characters — which is what a length over a UTF-8 buffer
naturally is, and the byte-or-character question surfacing in the only place it can so
far. **The choice is still the language author's**; that test is the line that changes
the day it is answered, and it is written down so the change is one line and not an
argument.

---

**Sixth time the same shape, and the first one where I wrote the test before the
measurement and the test was wrong.** I asserted a record's own `length` field still
reads — reasonable, and false: the name-based rule swallows it. It is now a skip with
the reason, and the working assertions are the four that survive measurement.

  a capacity floor that could not fire
  an enum whose read was never tested
  a refusal naming a host import as a literal
  a hoisting verified byte-for-byte that did not work
  a gate that lost refusals and could not say so
  a string length asserted before it was measured

**Five were caught by asking a second question. The sixth was caught by asking the
first one.**

### BUG-WASM-49 — `stringNames`: a string, a list and a record are all i32 (part closed)

**`addressNames` cannot answer "what does this value hold", because a string, a list
and a record are ALL i32.** That one fact is the reason for every string bug measured
so far:

```
  "ho" + "la"                 → 24        = 8 + 16 — two ADDRESSES added
  "hola".length               → 8.48e-314 a field read of a record layout
  { length: 99 }.length       → 0         swallowed by the LIST rule
```

So `stringNames` is the fourth kind, propagated the way `addressNames` is: a literal
whose kind is `string` names a string, a `declare` or `assign` that receives one names
a string, a `+` with a string operand produces one, and a field written with one is a
string field. A short fixpoint, because `let a = "x"` has to reach a `let b = a` that
was written above it.

**`.length` consults it, and the literal works.** Measured, before and after:

```
                              before                          after
  let s = "hola"; s.length   arraylength → 4    ✓            4  ✓
  "hola".length               loadfield   → garbage ✗        4  ✓
  { length: 99 }.length       arraylength → 0     ✗            0  ✗   (below)
```

---

**The third is not the emitter's rule and fixing the rule did not fix it.**
`stringNames` is consulted FIRST, and a record is not a string, so the question is
asked properly and answered "no". The value then reaches `isListValue`, which says
yes — because **`listNamesOf`, in the lowering, marks a name as a LIST because the
source has a `.length` member on it.** A rule about the SHAPE of the program, one
layer above the emitter, and it has been swallowing every record with a field called
`length` for the whole project.

**So the family is now one layer higher than this entry, and that is the point of
writing it down:**

- a record field written from a string literal      (the emitter)
- an array element written by `push`                (the emitter)
- a string's `.length`, which needed the header     (the emitter)
- a record with a field called `length`             (**the lowering**)

**Same defect, four times: a rule keyed on a NAME where a fact about the VALUE is what
is needed.** Two were fixed where they were found. This one is a different file, and
knowing that is worth more than fixing it in the wrong place.

---

**And what it makes possible, which is the part that matters for the corpus.** `+` on
two strings was adding their addresses because the emitter could not tell which
operand was a string. With the fact in place the question is answerable, and the
header written in BUG-WASM-48 is what a concatenation needs to allocate against:

```
  fn __concat(a, b) {  lenA = a[0]; lenB = b[0]
                      new = alloc(8 + lenA + lenB + 1)
                      copy(a+8, new+8, lenA); copy(b+8, new+8+lenA, lenB)
                      store(new, lenA+lenB); store(new+4, lenA+lenB); store(new+8+…)
                      new }
```

That is bytecode this backend has not written before, and it is the next piece. The
twelve tests here include the two that were skips yesterday and the one that is still
one, with the reason it is still one.

### BUG-WASM-50 — `+` concatenates two strings (part closed)

```
  "ho" + "la"     → 24    = 8 + 16, two ADDRESSES added
  ("ho" + "la").length  → 4
```

**A string, a list and a record are ALL i32**, so with nothing able to say which
operand was a string, `+` did the only thing `i32.add` can do. The fix is not a new
operator and not a special case in the lowering — **it is arithmetic over a header
that had to be created first**:

```ts
  lenA = a[0];  lenB = b[0];  total = lenA + lenB        // BUG-WASM-48 put the header
  new  = alloc(8 + total + 1)                            //   there, with the length
  copy(a + 8, new + 8,         lenA)                     //   at offset 0
  copy(b + 8, new + 8 + lenA,  lenB)
  store 0 at new + 8 + total
  store total at new + 0  and  at new + 4
```

**Two pieces, in this order, and the order is the whole of it.** BUG-WASM-48 put a
length at offset 0; BUG-WASM-49 made the operand's kind knowable. Either alone leaves
`+` adding addresses, because there is nothing to allocate against and nothing to say
it is a string. **A concatenation is not a feature, it is arithmetic over a layout and
a fact.**

---

**`emitMemoryCopy` already existed**, hand-emitted as `0xfc 10` — the second time
today that reading the opcode table and guessing was wrong, and the second time the
measurement settled it. `push` past its initial capacity was tested afterwards and
works up to forty elements, so the growth path was never in doubt; only my
inference was.

---

**The result is a NEW block on the heap**, so a `+` inside a loop allocates once per
evaluation, exactly as an `arraylit` does. There is no collector yet. That is a known
cost and it is written here so it is a decision rather than a surprise later.

---

**And `+` opens a question that is bigger than `+`.** A concatenation is a fresh
block, and string equality here is ADDRESS equality:

```
  ("ab") == "ab"          → 1    the same interned block
  ("a" + "b") == "ab"      → 0    a NEW block, compared by address
```

**Which is right for interned literals and wrong for everything a program builds.**
Every real comparison puts a built string against something else, so this is the next
thing `+` forces open — and it is a decision about what `==` means on strings, not a
mechanism. `it.skip`, with the measurement beside it.

**String + NUMBER is also still open**, and deliberately: turning a number into a
string is a FORMATTING decision — how many digits, what for a fraction, what for a
negative — and it is not made here. `"line " + 3` is still `i32.add`. Also
`it.skip`.

---

**Two tests here were wrong before they were run, which is the eighth time and the
one I would most like to stop repeating.** I asserted a concatenated string's address
was `> 65536`; 65536 is the heap base and is exactly right for the first block
allocated. The bound is `>=`. **A test written from a plausible story about the
implementation is a test of the story**, and the story was "somewhere in the heap",
which is not a number.

### BUG-WASM-51 — a string's element STRIDE is eight, so only index 0 read (closed)

```
  "hola"[0]        → 104  ✓   ('h')
  "hola"[1]        → 0    ✗   now 111
  let s = "hola"; s[2] → 0    ✗   now 108
  ("ab" + "cd")[1]  → 0    ✗   now 98  ('b' — index 1 of "abcd")
  [10, 20][1]      → 20   ✓   a list is eight-wide, and stays so
```

**`emitElementAddress` computes `base + 8 + (index << 3)` — eight bytes per element,
always.** A string's bytes are one wide, so index 1 was read from `base + 8 + 8`
instead of `base + 8 + 1`, and found nothing that looks like a character.

It is a **parameter** now — `emitElementAddress(base, index, ctx, buf, stride = 8)` —
and the guard is `if (stride !== 1)`, because a multiply by one is the identity and
the shift only has to happen for the eight-wide case. The default stays eight, and a
test asserts it, because a default that quietly became one would make every array in
the corpus read the wrong slot.

---

**And index 0 is the one case that cannot tell the difference, because `0 << 3` and
`0 << 0` are both zero.**

**That is now the THIRD first-element-only bug in this project, and every one of them
was a stride rather than a width or a data problem:**

- a `storeelement` at index 0 that worked and at index 1 that did not (the `Set`)
- a scan that found the first element of a list and none of the rest
- and a string index

**So the rule worth keeping: an element access that works at index 0 and nowhere else
is a STRIDE problem, not a width problem.** Index 0 multiplies by zero, so it agrees
with every stride there is, and it is therefore the one case that proves nothing. A
test written with two elements catches it; a test written with one does not, and
**every test anyone writes by hand has one in it.**

---

**The first attempt broke seventy tests, and why is part of the entry.** The patch
spliced by line index and started one line ABOVE the shift, so the three lines it
replaced ended with the `i32_add` that combines `base + 8` with `index * 8` — and
deleted it. `invalid value type 'noexn'`, and the repair was restoring from the green
copy, which is what an editor with an undo button is for.

**A line-index splice is a text edit with the safety removed.** The second attempt
used the WHOLE function as the anchor and applied in one verified pass. The general
rule underneath it: **when an edit is by position, a bigger anchor is not ceremony
— it is the only thing standing between a guess and a broken build.**

---

**What it opens, and it is the whole rest of the string layer.** `split`, `slice`,
`trim`, `replace` and `includes` are all written IN THE LANGUAGE once a program can
read a character and write one back with `+` — and `path`, 45 gaps of pure text with
no I/O and no operating system, sits on top of them. **None of that was expressible
until a program could index a string, and one that only reads index 0 is not enough
to write any of it.**

**The width is BYTES**, which is the byte-or-character question surfacing in the only
place it can so far. A length header over a UTF-8 buffer counts bytes and indexes
bytes; that is consistent, and changing it is the language author's decision.

**Known and not decided: there is no bounds check**, and a list does not have one
either — `L[99]` on a two-element list reads whatever eight bytes follow it. A
language can trap, return a sentinel, or lie, and Nodeon has not chosen. `it.skip`
with that as the reason, because the honest answer here is a decision rather than a
number.

### BUG-WASM-52 — `slice` is 45 uses, and the dispatch asked about a temp (open)

**Forty-five uses in the corpus, and the gate said three**, because it counts one
item per PROGRAM. The shapes are all arithmetic over a length already at offset 0:

```
  s.slice(n)      from n to the end
  s.slice(a, b)   a byte range
  s.slice(-k)     the LAST k bytes — a negative index counts from the end
  s.slice(0, -1)  drop the last byte
```

**So it is a byte copy and not the byte-or-character decision.** Every index is an
offset into a buffer whose length is in bytes. A CHARACTER index cannot even be
written yet, because a character count is not what a length header holds.

This is the piece the rest of the string layer is written on: `split` (23), `trim` (13),
`replace` (58), `includes` (55), `startsWith` (30), `endsWith` (28) and `path` — 45 gaps
of pure text with no I/O and no operating system — all begin by asking for a range of
bytes.

---

**The attempt failed on a question asked of the wrong value, and that is the whole of
it.**

`s.slice(2)` lowers to an indirect call on a `loadfield` of `s`, and the receiver that
reaches the emitter is the **TEMP** the `loadfield` produced — not `s`.
`isStringValue` asks `stringNames` about it, and the string fixpoint marks literals,
`declare`, `assign`, `storefield` and `+`… **but not a READ of a string.** So the
question was asked and answered "not a string", and every shape was refused:

```
  s.slice(2)      → refused      s.slice(1, 3)   → refused
  s.slice(-2)     → refused      s.slice(0, -1)  → refused
```

**This is the same gap `isListValue` documents in its own comment** — a value that
arrives from a field read is an address and is in nobody's set. It was read at the time
and not applied to the fourth kind.

---

**And the thing I assumed, which is the part worth keeping.** `L.slice(1)` is all over
the corpus — `args.slice(1)` in `index.no` a dozen times, `stmts.slice(0, -1)` in the
generator — and I took it as obviously working. It is refused too.

**A method that appears often enough in the corpus is not evidence that it works; it is
evidence that nobody tried it.** `slice` looked finished because it is everywhere, and
it had never run. I would have shipped a helper that did nothing.

The helper was written and then reverted, because **dead code that reads as implemented
is worse than an honest refusal** — and the gate cannot tell the two apart either.

---

**Half of it landed, and the other half is why `slice` is still refused.**

`stringNames` now marks a READ:

```ts
  if (inst.op === "loadfield") {
    const o = valueName((inst as any).object);
    if (o && mine.has(o)) claim(nameOf(inst));
    if (!(inst as any).computed && stringFields.has(String((inst as any).field))) {
      claim(nameOf(inst));
    }
  }
```

A read of a string yields a string, by either route — the object being one, or the
field being one. **The suite is unchanged at 965 and the gate is unchanged, which is
the honest result: the fact was incomplete and now it is not, and no program in the
corpus has a `slice` that is not already refused for something else.**

---

**And `slice` is still refused, with the open question now down to two.** The fixpoint

1. **`ctx.current` is not the key `isStringValue` looks under** — it reads

2. **`inst.args[0]` is not the receiver.** The branch assumes the receiver is the

**Two cheap measurements separate them, and neither needs a change to the compiler:**
print `stringNames` and the receiver's name for one program, and print `ctx.current`

rather than another guess.

**`slice` on a LIST does not exist at all**, and that one needs no investigation — it
is an eight-wide element range rather than a byte range, it is refused everywhere,
and `args.slice(1)` appears a dozen times in `index.no` alone. **A method that appears
often enough in the corpus is not evidence that it works; it is evidence that nobody
tried it.** That is why it read as finished.

---

**The helper was written and reverted**, because dead code that reads as implemented is
worse than an honest refusal — and the gate cannot tell the two apart either. What is

### BUG-WASM-53 — `stringNames` cannot see past a CALL (open)

**A probe answered this in one line, and it ruled out both things it was written to
test:**

```json
{"current":"f", "name":"_t3", "hasThisFn":false,
 "setForThisFn":["_t0","s","_t1"], "defOp":"call", "stringFields":[]}
```

1. **`ctx.current` is `"f"`** — the right key, so the lookup is not looking under a
   function that does not exist. **Ruled out.**
2. **The string fixpoint did its work.** `stringNames["f"]` holds `_t0`, `s` and
   `_t1`, so the read of `s` was claimed and the read fix landed. **Ruled out as a
   cause** — and that is the fix from BUG-WASM-52 being confirmed rather than
   assumed.
3. **The name being asked about is `_t3`, and its definition is a CALL.**

**So the receiver that reaches `isStringValue` for `s.slice(2)` is not the field read
of `s` — `_t1` is that, and it IS a string — it is the RESULT OF A CALL**, and nothing
in the fixpoint follows a call.

---

**The missing rule is one line and it is not about reads at all:**

```
a call that RETURNS A STRING produces a string
```

That is a **per-function fact** — the mirror of the `returnsAddress` this file already
computes — and there is no way round it from inside one lowering pass, because the
callee may live in another file and `lowerToIR` sees one file at a time. **This is the
same cross-file fact problem three times over now**, and every one of the three looked
like a local mistake:

- a nested function's captures (BUG-WASM-35) — a fact that crosses a function boundary
- a module-level constant (BUG-WASM-45) — the same
- and now what a call returns

---

**The pattern underneath all three, and it is the one worth keeping:** something
crosses a boundary — a closure, a module, a call — and a rule that used to be answered
**locally by a name** starts being answered at the point of use, where nothing is
left to answer with. Each time the fix was the same shape: **a fact for the whole
program, decided once**, the way `addressNames` and `arrayElementKind` already are.

**And the reason it is a good sign is that the probe worked on the first run and
answered a question two readings could not.** A diagnostic that is removed afterwards
is worth more than one that stays: it costs one file write per question and it is gone
before anyone reads the code and believes it.

### BUG-WASM-54 — a member call does not pass the receiver (open, and it is big)

```json
{"op":"call","field":"slice","target":"_t3",
 "callee":{"kind":"temp","id":"_t1"}, "argCount":1,
 "args":[{"kind":"temp","id":"_t2","defOp":"literal"}],
 "receiver":null, "object":null, "indirect":true,
 "keys":["op","target","callee","args","indirect","inTry"]}
```

**Read `argCount` and `keys` together. There is one argument — the literal `2` — and
the instruction has no field for a receiver at all.** The call is
`call(loadfield(s, "slice"), 2)`: the member's VALUE and the written arguments, with
the object dropped on the floor.

---

**This is why the two measurements before it were both reading the wrong thing.**

- The first asked `isStringValue` about `inst.args[0]` and found its definition was a
  CALL. That was correct and it was a clue: `args[0]` is not the receiver, because the
  receiver is not in `args`.
- The second guessed the missing rule was `returnsString` — a call that returns a
  string produces a string. **`returnsString` is real, correct, and now landed**, and
  it changed nothing here, because the receiver is not a call result at all.

**So BUG-WASM-53's conclusion was half right.** The rule about calls is real and worth
having; it was not what was wrong with `slice`.

---

**And this is one defect behind most of what the gate has been calling "host calls".**

The list is `join`, `log`, `existsSync`, `readFileSync`, `writeFileSync`, `cwd`,
`resolve`, `dirname`, `basename`, `get`, `slice`, `replace`, `includes`,
`startsWith`, `endsWith`… Every one of them is a call **on a receiver**, and the
receiver is not being passed to any of them.

**They were never forty missing features. They are one missing argument.**

---

**What the fix is, and why it is a design question rather than a patch.** A call that
passes the receiver is a METHOD CALL, and WebAssembly has no method call: every call
is `call(index)` on a function index. So passing the receiver means either:

1. **The receiver becomes the first argument**, the way the list helpers already do —
   `fn __slice(list, from, to)` and the call site pushes the object first. The
   `receiverFirst` flag and `capturesByFunction` machinery in this file are already
   shaped for exactly that, so this is the cheap one and it matches the house style.
2. **The receiver becomes an environment**, and the callee is a closure — which is
   what `fnvalue` and the closure thunks already do.

**Either one is a few lines. What has been missing is that nobody looked at the
instruction before counting forty gaps.** The gate is honest about what it was told:
there is no host to ask. **The refusal names the symptom and not the cause**, and that
is why three turns of string work went into a problem that has one line in it.

---

**THE RECEIVER IS NOW PASSED. That is the landing, and it is one line.**

```ts
const receiverFirst = calleeNode?.type === "MemberExpression" && !isDirect;
const args: IRValue[] = receiverFirst
  ? [lowerExpr(calleeNode.object, b), ...expr.arguments.map((a) => lowerExpr(a, b))]
  : expr.arguments.map((a) => lowerExpr(a, b));
```

The receiver travels as argument zero — which is what WebAssembly needs, since it has
no method call and every call is `call(index)` — and `receiverFirst` is the flag the
emitter already reads to know an argument is a record, so nothing new was introduced.
Only the argument that was missing.

**No program in the corpus is unblocked by it yet**, and the gate is unchanged at
`valid 3`. That is the honest result: every one of those programs fails for another
reason too, and the gate was never going to show this one because it names a SYMPTOM
in forty places and a CAUSE in none. **What it buys is that `has` and `add` now have a
receiver to ask about**, and every string method that dispatches on one is one step
closer.

**`slice` is reverted, and the two mistakes that killed it are the useful part.**

It compiled — the branch finally fired, which is what the receiver was for — and then
every shape trapped with `memory access out of bounds`. The cause was mine:

```ts
  get(toL);            // ← pushes to `buf`, the MAIN buffer
  get(fromL);
  buf.push(OP.i32_sub);
  bb.push(OP.i32_const);   // ← and the constant goes to the callback's
  ...

```

**A callback that builds a sub-expression has to build ALL of it.** Three of the four

The second mistake was not in the compiler at all: **the probe defined `fn f` and called

### BUG-WASM-55 — one byte comparison under everything that is left (open, specified)

**`includes` 55, `startsWith` 30, `endsWith` 28 — 113 sites, and all three are the
SAME comparison: n bytes of one block against n bytes of another.**

```
  s.startsWith(p)   eq(s, p, 0,          0,           len(p))
  s.endsWith(p)     eq(s, p, len(s)-len(p), 0,          len(p))
  s.includes(p)     the same, at every offset until one matches
```

**And it is not the byte-or-character decision.** Every index is an offset into a
buffer whose length is in bytes. It is also not a formatting decision. It is the
same arithmetic `slice` was, with the answer being a bit instead of a block.

---

**The shape, and the part that is new ground:**

```wat
  i = 0
  block $exit
    loop $cont
      local.get i; local.get n; i32.ge_u; br_if $exit      // i >= n, stop
      (a + 8 + fa + i).load8_u  !=  (b + 8 + fb + i).load8_u
      if  return 0  end                                     // first mismatch wins
      i = i + 1; br $cont
    end
  end
  return 1
```

**`block`/`loop`/`br_if`/`br` are all declared in the opcode table and all already
emitted here** — checked, not assumed — so a loop in the emitter is not new
machinery. What IS new is a loop written as raw bytecode rather than lowered from
`while`.

**The opcodes are in now.** The table was missing three of the four unsigned
comparisons, and `i32_gt_u` — the one that WAS there — was checked against the spec
and is correct:

```
  i32_lt_u  0x49   added
  i32_gt_u  0x4b   was already correct
  i32_le_u  0x4d   added
  i32_ge_u  0x4f   added
  select    0x1b   added earlier, for the clamps
```

**Why a byte scan needs the unsigned ones at all.** It asks `i >= n` about a LENGTH,
and the signed comparisons do not answer that: a length above 2^31 is negative, and a
negative `i` passes `< n` for every `n`. A signed loop over a byte count is a loop
that ends when it happens to, which is the same shape as every other off-by-a-sign in
this file's history.

**This is a table and nothing else** — no emitter logic, no codegen path — so it is
as safe as a change gets, and it removes the last thing standing between the design
above and writing it.

**And the shape of the hole is the same as the one before it:** an opcode the table
never needed until a program tried to use it. Neither `select` nor `i32_ge_u` was
wrong. They were ABSENT, and nothing could tell until something emitted them. **A
capability gap that has never been exercised is indistinguishable from a capability
that does not exist** — and the way to tell them apart is to write the smallest thing
that needs it, which is exactly what the five empty `i32_*_u` rows just did.
---

**Why it is written down and not written now.** `slice` is the same shape — allocate,
copy, a loop or a scan — and it took three turns: the receiver fix, a bad opcode, a
size expression pushed to the wrong buffer, and a probe that called `exports.run` on a
function called `f`. Each of those was found by the suite in under a minute, and each
cost the tree a restore.

**What landed this session is the part that every one of these methods needs and none
of them had:**

  the string layout            `[len][cap][bytes][NUL]`
  `stringNames`                reads AND calls, so a receiver is knowable
  `returnsString`              the mirror fact, for the callee
  the STRIDE                   one byte for a string, eight for a list
  `+`                          concatenation, and a block to allocate against

long session where five consecutive positional edits have already shown what tired

### BUG-WASM-56 — a seeded PARAMETER is not visible to the module analysis (open)

**The string methods were written in the LANGUAGE, not in bytecode, and that was the
right architecture — but the run says where the real wall is.**

```
  fn __str_startsWith(s, p) {
    let i = 0
    let n = p.length
    if s.length < n { return 0 }
    while i < n { if s[i] != p[i] { return 0 } i = i + 1 }
    return 1
  }
```

Every part of that lowers. `while` becomes blocks, `s[i]` is the one-byte load of
BUG-WASM-51, `.length` is the header. **Zero new emitter bytecode, and the loop that
`slice` needs and does not have is not needed here at all** — the LOWERING writes loops.

---

**And the run says exactly what is missing — and the fix that followed did not change
it.**

```
  s.startsWith("hol")   → 0     want 1     the false number
  s.startsWith("")      → 1     want 1     an EMPTY needle matches
  s[1]                  → 111             the byte read is RIGHT
  endsWith, includes    → invalid module
```

**The byte read works. The comparison does not.** The seed is the obvious suspect:

```ts
lowerFunction(…, { s: "address", p: "address" }, …)
```

and it IS a real defect on its own terms: `mod.arrayKinds` carries the seed,
`lowerFunction` merges its builder's `arrays` into the module's table — but the set that
says what a name holds is filtered by `names.has(id)`, and `names` holds the TARGETS
of instructions. **A parameter is the target of nothing**, so a seeded parameter was
being thrown away by the very set that exists to record it. That fix is IN:

```ts
const seeded = fn.params.filter((p) => mod.arrayKinds?.[p] === "address");
arrayNames[fn.name] = new Set([
  ...Object.keys(mod.arrayKinds ?? {}).filter((id) => names.has(id)),
  ...seeded,
]);
```

**And `startsWith` still answers 0.** The suite is unchanged at 965 and the gate at
`valid 3`, so the fix is inert for this case: either the fault is elsewhere as well, or
this was never it.

**It stays anyway, and the reason is the same as the receiver.** It is true, it is
general, and it affects `map`, `indexOf` and `filter` as much as anything else — a
parameter the lowering seeded really is a list, and the analysis really was dropping
it. **A correct fix that is not THE fix is still a correct fix**, and the difference
between those two sentences is the difference between measuring and assuming.

### BUG-WASM-58 — a TERNARY becomes a string literal (closed)

### BUG-WASM-59 — a PARAMETER can be a string, and only the caller knows it (closed)

`stringNames` is a fixpoint over the IR: it claims the target of every string literal and
follows `let`/`=` from there. **A parameter is never assigned a literal, so it can never
be claimed** — and `isStringValue` is exactly the predicate that chooses one byte per
element instead of eight.

```

```

correctly in the caller. **The same name in two functions, two different widths** — the
caller's local `s` was a literal and the helper's `s` was a parameter, and only one of
those is something the fixpoint can see.

`{ s: "address", p: "address" }`, and `arrayKinds` means *a list whose elements are eight
bytes wide* — which is the very fact that decides the width. The lowering needs a fact
here (a string is an indexable block with a length header, so it lowers exactly like a
list) and the emitter needs a **different** one. One table could only carry the first.

`IRModule.stringSeeds`, and **deliberately not into `arrayKinds`**:

```ts
if (kind === "string") { b.arrays.set(name, "address"); continue; }  // the lowering
for (const n of mod.stringSeeds?.[fn.name] ?? []) claim(n);          // the emitter
```

in this project that a fact established on one side of a call boundary has been treated
as if it crossed: capture, module constant, receiver, seeded parameter, seeded string, and
the seed's table. Every one of them looked like a local arithmetic mistake.

The regression test is the one that hands the function a string it did not build. **Every
other test in that block has a literal on the other side of the call**, which is the one
case where the caller's own `stringNames` happens to agree with the helper's — by name
collision, not by knowledge. A suite of literal-only tests would have stayed green through

**CLOSED, and the fix was one `default:` — because the statement path had already been

### BUG-WASM-63 — a ternary is an `if`/`else` that produces a value (closed)

that ordered the work.

**A branch already produced a value through a merge block.** The `IfStatement` lowering

### BUG-WASM-61 — `fn(x) = expr` returned 0, in every shape (closed)

The generator has always applied the implicit return and the lowering did not, so a

### BUG-WASM-64 — a template literal with no hole is a string (closed)

### BUG-WASM-65 — a number in a string is an UNMADE DECISION (open, asked)

The question is not what a template does — it is what `String(1)` is, and the same
answer governs `"prefijo: " + x` and `x + "!"`, which is a much larger surface than
templates. Three ways to answer, and they differ in cost rather than in taste:

- **JavaScript's.** `1` → `"1"`, `0.1+0.2` → `"0.30000000000000004"`. Never loses
  information — that is the shortest decimal that round-trips to the same double — and
  every ported program behaves identically.
- **Rounded.** `0.1+0.2` → `"0.3"`. More readable, which is the language's argument, and
  the text no longer round-trips to the same number, so a ported program prints
  differently.
- **No conversion.** A number in a string is a refusal. Honest and free today, and it
  blocks the 67 holes and most of `+`.

**Asked, not guessed.** Meanwhile the two shapes that can be answered without choosing
anything are done: a template with no hole is a string, and `+` between two known strings
concatenates.

### BUG-WASM-66 — `"texto" + x` with `x` of unknown kind answered a denormal (closed)

`+` concatenates only when BOTH operands are known strings, and otherwise fell to
`i32.add` on an address — so a string and a value of unknown kind added a pointer to a
pointer:

```
fn name(s) = s + "!"   →  name("hola").length  =  1634496360     want 5
let g = fn(x) = x + "!"  →  g("hola")  =  0                    want "hola!"
```

Both silent. **That is not a refusal, it is a wrong answer that looks like a number.**

**And where the refusal went was wrong twice before it was right.** First in the emitter
as a `throw` — which made the gate fail, because it has said since before this work that
the compiler must never throw on real code: *a refusal is a reported gap, a crash is a
defect in the compiler*. Three corpus programs reported `threw` and I had spent the turn
converting refusals into crashes. Now it is a **diagnostic**, which is what a diagnostic
is for.

**What it does not catch, and the gap is real:** `s + t` where neither side is known.
Both look like numbers, so they add, and if they were strings the answer is a denormal.
Telling those apart is BUG-WASM-65, and it is written down rather than guessed at.

The rule that shipped is recursive — a string literal, **or** a `+` whose own two sides
are both strings. The second clause is not decoration: `"a" + "b" + "c"` is
left-associative, so its left operand is the `binop` `"a" + "b"` and not a literal, and
the first version of the rule **refused a concatenation that had worked since
BUG-WASM-49**. The suite caught it in seconds. A rule written about the shape of a thing
has to be written about the shape the thing actually has, and `a + b + c` is not shaped
like `a`.

### ~~"A function result is f64 and a list is i32, so you cannot return a list"~~ — RETRACTED

assumption that costs hours: the claim was the *conclusion* of reading the local map,
where anything not pinned is declared f64. The conclusion was reasonable and the local
map is not the whole of the type system — `returnsAddress` is a second source, and it
disagreed. **Reading one of two sources and concluding from it is how a limitation gets
written down as a fact.**

It stays retracted rather than deleted, like BUG-WASM-41, because the sentence was
believed and would otherwise be believed again. The retraction is the measurement, and
the measurement is what is worth having.

### BUG-WASM-67 — `.length` of a list returned by a call, read in one step (closed)

The one shape in the family above that did not work, and the only one:

```
fn g() { return [1, 2, 3] }
fn f() { return g().length }     →  1.6975966329e-313     want 3
fn f() { let xs = g()  return xs.length }  →  3            PASS
```

`1.6975966329e-313` is a **denormal**, and that is the whole diagnosis: three as the
length and eight as the capacity, read as eight bytes and interpreted as a double. So the
read took the RECORD branch — a field read with no offset — where the LIST branch would
have read four bytes at offset 0.

**And `isListValue` cannot answer it, because the receiver is a TEMP.** The predicate
follows one step of definition for a `loadfield` into `arrayFields`, and a call result is
neither a name the module marked nor a field read. The fact that does exist is
`returnsAddress`, and it says the function gives an address without saying which of the
three address-kinds it gives.

**The fix that reads like the obvious one is a regression, and measuring first is what
showed it.** Teaching `isListValue` about calls would take the record branch away from
four shapes that are right today, because `isRecordValue` consults `isListValue` FIRST:

```
g().v = 5 ✓    g()[1] = 2 ✓    g().startsWith = 1 ✓    g()[1] on a string = 111 ✓
```

So the new knowledge is a **separate predicate** asked at exactly one site — the
`field === "length"` read — where the answer is the same either way, because a list's
header is at offset 0 and a string's is at offset 0. All four of the shapes above are
tests now, as a fence around that decision.

**A note on how this was found, because it is the third time in this file.** The claim
being tested was "a function cannot return a list", and the test that "confirmed" it was
one program that returned a list **built by `push` and read in one step** — three
separate things in one line. Decomposed: `push` alone works, returning it works, reading
it through a name works, and **the one-step read is the only broken piece**. A test that
carries three untested assumptions in it does not confirm anything; it picks which one
you go looking at, and the one it picks is not necessarily the broken one.

### BUG-WASM-68 — indexOf, lastIndexOf and charCodeAt (closed)

**The three string methods that return a NUMBER, and so build nothing.** `split` and
`trim` are not here and the reason belongs in the file people reach for next: both
return a value the language cannot build yet. A substring is a **NEW block on the heap**,
and a helper written in Nodeon has no way to allocate one — `emitStringConcat` allocates
in the emitter and there is no `new string` in the language. These three return a number,
so the byte comparison and the loop are the whole of it.

The bodies were written out and run on **locals** before they became helpers, because a
failure with a seeded parameter in the picture cannot be told apart from a failure of the
body — that is how BUG-WASM-57 and 59 were separated from the seed everybody blamed.

Two edges fall out of the loop rather than needing a branch, and both are what JavaScript
does: `lastIndexOf` walks DOWN (`start >= 0`), which is why the answer can be -1, and an
empty needle lands on the length.

**`indexOf` takes no `from` parameter, on purpose.** A default would need a wasm
parameter the call site does not push, and a stack short by one is an invalid module. So
this is the arity that works, and `indexOf(haystack, needle, from)` is a **named refusal**
rather than a silently wrong index.

### BUG-WASM-69 — the method dispatch was by NAME, and the receiver's kind decided nothing (closed)

Measured on both sides, and **neither was right**:

```
before — `indexOf` in the LIST table only, so `s.indexOf("hola")` ran the LIST helper
         over a string block and answered -1. No diagnostic, no trap.
after  — `indexOf` added to the STRING table, which is checked FIRST, so the six
         existing list tests stopped compiling to the right thing.
```

A name in two tables belonged to whichever table was reached first, and **that is a
symptom of the design, not of the two changes**: the list side of the question has
always had an answer — `b.arrays` says a name is a list — and the string side did not
exist, so the tie was broken by table order.

So the lowering now keeps a `stringNames` set, marked at the two places the syntax can
prove it: a string **literal**, and a `+` whose two sides are already marked. The
second is the recursion, and the reason is the same as BUG-WASM-66's: `a + b + c` is
left-associative, so the left operand of the second `+` is itself a `+`, and a rule that
only looked at literals understood a `+` in place and not a `+` behind a name.

**And the rule asks for POSITIVE EVIDENCE, only for a name the two tables share.** That
half is what kept the suite green. A name only the string table has — every one of
`startsWith`, `endsWith`, `includes`, `charCodeAt` — dispatches exactly as it did before,
which is why `startsWith` on a **parameter** still works and why nothing that worked
stopped. A rule written as "unless it is a list" would have broken a list returned by a
call and then indexed; asking for proof cannot.

**What is still open, and named:** a string that is a **parameter** or a **call result**
cannot be proved in the lowering, so a shared name on such a receiver still reaches the
list helper. That is the same boundary as BUG-WASM-59 and it is written down rather than
patched, because closing it means the decision has to move to the emitter — which is
where `stringNames` already exists for a whole module, and the lowering is not.

**Three of my own measurements were wrong in this one piece**, all in the same shape:
a helper function I never declared (three TRAPPEDs), a count of the string instead of
the needle (`lastIndexOf("")` expected 4 on a five-character block), and an index
mis-read by eye (`"hola".indexOf("ola")` is 1, not 2). **The compiler was right in all
three and I was the one who had to be corrected** — twice by the suite and once by
reading the string again.

### BUG-WASM-70 — a `slice` PRIMITIVE, attempted by hand in bytecode and REVERTED (reverted)

**The finding that motivated it is right and stays.** `trim`, `replace`, `split` and
`join` all reduce to "copy some bytes into a fresh block", and **a helper written in the
language cannot do it**: there is no way for one to reserve memory, because allocation is
`emitAlloc`'s and there is no `new string` in the language. That is a real wall, and it
is the one standing between the corpus and `path`.

The attempt was to add ONE emitter primitive — allocate, copy, header — the way
`emitStringConcat` already does for `+`, and then write `trim` and the rest as Nodeon
source on top of it. That architecture is right. **The execution was not.**

```
… 20 0c 21 06 20 06 41 00 6a 2b 00 00 21 07 20 07 0f …
                                          ^^ i64.load where i32.load belongs
```

while the `memory.copy` it emitted was byte-perfect (`fc 0a 00 00`) and the body's
declared size matched the bytes exactly. **Thirty hand-written instructions, one of them
wrong, and the engine's message — "memory index 4 exceeds number of declared memories" —
pointed at neither.** Two rounds of guessing before the bytes were read, and the byte
that was wrong was not one I had been staring at.

**This is the same wall as the `slice` that took three turns and never worked, in a
different costume** — a helper's work written as bytecode by hand, this time with a copy
instead of a loop. The note about it says not to, and this run paid for it twice.

**So it is reverted, and `slice` goes back to a member call with no host** — a refusal
WITH A NAME. A module the engine rejects is not a language that is nearly there; it is a
language that answers with a broken module, which is the shape this project has spent the
night removing from every other corner.

**What the attempt leaves behind is the instrument**, `.mavis-probe/bytes.probe.ts`: it
dumps the module in sections, reads the body size, checks whether the declared length
matches the bytes actually emitted, finds every `fc` and shows the three bytes after it.
**Three questions in one run that would otherwise have been three rounds of guessing**,
and the first two answers ("the copy is fine", "the size is fine") are what narrowed the
last one to a single byte.

### BUG-WASM-71 — the `+` refusal only knew about LITERALS, and refused real concatenations (closed)

**A regression that shipped for part of this run, and no test caught it.**

```ts
const knownString = (e) => e.type === "Literal" ? … : e.type === "BinaryExpression" && …
```

The predicate behind BUG-WASM-66's refusal recognised a string LITERAL and a `+` of them,
and nothing else. So `s + "x"` and `"x" + s` — concatenations that have worked since

What caught it was a probe whose **control** was a `"a" + "b"` that stopped compiling.
The control existed to make the byte dump comparable, and it did a second job: it was the
only program in the run that used a name on one side of a `+`.

**The two rules needed the same predicate and I wrote them separately.** They now share
one, `receiverIsProvedString`, which knows an Identifier, a Literal and a `+` — and which
BUG-WASM-69 had already made necessary by giving the builder a `stringNames` set.

**Three regressions in one run, and not one of them was caught by the suite**: `s + "x"`
refused, `lastIndexOf("")` with a miscounted expectation, and an index mis-read by eye.
Two were mine in the tests and one was mine in the compiler. **A suite made of literal
pairs cannot see a rule about what a name is** — and every one of the three would have
been invisible to a gate that only runs the corpus.

### BUG-WASM-72 — the same primitive, a SECOND time, with the bounds in the right place (reverted)

The architecture argued for by the first failure is the right one, and it was tried:
**the clamping moved to the LOWERING as four ordinary `if`s**, where control flow is
already the lowering's job, and the emitter was left with a strict subset of what
`emitStringConcat` emits. It validated. Then it trapped, three separate times:

```
1  clamp(b, name, op, limit, value) called with the LIMIT where the VALUE goes.
   The one guard that emitted at all did the opposite of what was written, and the
   three that passed `null` emitted nothing:

     [entry] … declare _t1=5  declare _t3=10  arraylength  binop → branch
     [then]  assign _t1 = _t5          ← `from = len`, guarded by `from < 0`

2  `"0"` passed where an IRValue belongs:  f64.lt[1] expected f64, found i32.const
```

**All three are the same mistake: a hand-written stack sequence whose operands were not

primitive has to be **extracted from `emitStringConcat`**, not written beside it — so the

source address. Reuse is not tidiness here; it is the only thing that makes the arity
question go away, because the code that has it right stops being code I have to count.

**And the diagnosis of my own process, which is the transferable half:** two attempts,
each preceded by a measurement and each correct about the measurement, and both wrong in
the same unreviewed place. The measurements were sound; **the code between two
measurements was not, and nothing in my loop looked at it.** The instruments that found
each bug were different — the byte dump, the IR dump — and both were worth having. What
was missing was a step that reads the emitter code against an emitter comment before
writing bytecode into it.

### BUG-WASM-73 — the THIRD attempt, done the way the second one argued, and what survived it (reverted)

The second attempt's conclusion was not a third shape: **extract from
`emitStringConcat`, so the arithmetic stops being hand-written.** So that is what this
attempt did, and it is the first of the three where the shared code is not the variable.

`emitStringConcat`'s allocate / copy / NUL / header tail is now **`emitStringBlock`**,
parameterised by a list of pieces, with **`pushStrBase`** as the one helper both callers
use. **997 green before and after** — a correct change to working code, verified before
anything new was built on it. The `slice` instruction's whole body is then *one piece*
whose `src` pushes the base plus one offset, and the count is written out beside it:

```
pushStrBase  →  ONE value   (source + 8)
emitValue    →  ONE value   (from)
i32.add      →  consumes 2, leaves 1
```

It still trapped. **The lowering is now CORRECT and the IR dump proves it** — all four
guards, in the right order, which is exactly what the second attempt got wrong:

```
if _t1 < 0 { _t1 = 0 }      if _t1 > _t5 { _t1 = _t5 }
if _t3 > _t5 { _t3 = _t5 }  if _t3 < _t1 { _t3 = _t1 }
_t19 = _t3 - _t1            stringslice(from: _t1, count: _t19)
```

So the trap is in that one line of the emitter, and it was not isolated in the turn
available. **Three attempts in two turns is the signal**, and the instruction is reverted.

**What the three attempts are worth, in order of what they cost to learn:**

1. *The primitive belongs in the emitter, not in a language helper.* Allocation is
   `emitAlloc`'s and there is no `new string`. That is a real wall and it is still there.
2. *The bounds belong in the lowering.* `select` per bound in the emitter was the wrong
   place for them, and the argument order of a five-parameter helper is not something to
   get right by eye.
3. **The routine has to be extracted, not copied.** This attempt proves it the only way
   that counts: with the tail shared and tested, the unknown shrank from thirty
   instructions to one, and the IR dump proved the lowering was not the problem at all.

**The part that stays is the refactor**, and that is the first time in three attempts that
something survived. A `slice` now costs one piece, not thirty instructions, and whoever
writes it next starts from a routine 997 tests exercise rather than from a copy of one
that 997 tests happen to cover.

### Reverting removes the thing you need to diagnose it

The fourth turn measured instead of attempting, and the measurement **ruled out two of the

```
heap-shaped words in the first 4KB: NONE
```

### The local map, and the `local.get 3` that meant three different things

`local.get 3` is an INDEX, and four turns of reading it as a NAME is why the attempts kept
disagreeing. **`compileIRToWasmDesc` was already exported and nobody had used it for
this**: `WasmFunc` carries `locals: WasmValType[]` in index order, and `inferLocals`
assigns indices by a walk the IR can be replayed with — parameters first, then every
instruction's target in program order, plus the two operands a `storeelement` names.
Replaying that walk gives name → index → declared type, **with no change to the
compiler**, and it is now printed beside the bytes by `bytes.probe.ts`.

Validated on programs whose answer is known, because a map that is wrong in the same way
as the thing it measures is worse than no map:

```
let s = "hola"; return s.length

fn g(a, b) { return a + b }
  0  a     f64        1  b   f64        2  _t0   f64        3 = 3 ✓
```

**The third one is the interesting one, and the probe says so out loud rather than

the temps and not of the bindings, and a rule written about one of them does not hold for

That is the state the fifth attempt starts from, and the difference is that it is a

### BUG-WASM-75 — destructuring, which needed no new fact (closed)

`const { a, b } = cfg.db` and `const [x, y] = xs` are **one `declare` per name over ONE
lowered value**, and every read they need already existed: a field read is a `loadfield`
and an element read is the same instruction with a computed index. **No new emitter
bytecode and no new type** — it needs a fact the backend has, not a new fact, and that is
the whole difference between this and the slice.

Three details, and the first is the corpus's own shape:

- **A key can be a PATH.** `const { host, port } = config.db` parses the key as
  `config.db`, so the field to read is the last step and the receiver is everything
  before it. `features.no` writes it three times, and an implementation that reads the
  whole key as a field name gets nothing. One extra `loadfield`, found by reading the
  generator's `emitObjectPattern` rather than by guessing.
- **The value is lowered ONCE** and every binding reads through that one IR value.
  Lowering `stmt.value` per property would re-emit its instructions once per property,
  which for `const [orig, alias] = n.trim().split(...)` is a call per element.
- **A `null` element is an elision** — `[a, , c]` — and honouring it costs one `if`.

**A rest element is refused by name**, and that is the one honest gap: `[a, b, ...rest]`
needs a list slice, and the list has no `slice` (BUG-WASM-76). A binding that holds an
address nobody can index would be worse than a refusal, and this backend has spent the
night removing exactly that shape.

**And the frontier moved, which is the check that matters.** `DestructuringDeclaration` was
in 7 programs and is now in none of them, while the number of programs with some gap went
40 → 41 — one program now reports its *next* wall instead. That is what a fixed form
looks like from outside.

**My probe was wrong first, and the way it was wrong is worth writing down.** The first
run reported `inst.exports.f is not a function` on all nine cases, which reads exactly
like the compiler having dropped the export. It had not: the probe had a parameter called
`src` and never wrapped the body in `fn f() { … }`, so it compiled a bare list of
statements and the module published only `memory`. **A missing export and a call to a
function that was never compiled produce the same message**, and the fix was in the
instrument.

### BUG-WASM-77 — a backend-specific refusal had nowhere to live, and it broke the working backend (closed)

### BUG-WASM-78 — a block carries its kind (closed)

**Done, and the bug the first attempt could not name is named.** Applying it as TWO
pieces with a suite run between them — the four static interners, then the runtime
allocator — turned "sixteen denormals in an interaction I never identified" into "the
runtime allocator", and the second run had one failure.

```
step 1, the four interners          → 1004 pass   (the safe half, proven on its own)
step 2, emitAlloc                    →  16 red, all of them records
   one `& 7`                        →   1 red, and it is a slot-size assertion
   the assertion written as itself   → 1004 pass
```

**The bug: the allocator aligns the pointer DOWN, and the tag broke the invariant that
made that safe.** `ptr - (ptr & 7)` was harmless only because every block's size was a
multiple of eight — length, capacity and elements are all eight-byte units, so `end`
always landed aligned and the next block began exactly where this one ended. **A four-byte
tag makes `aligned + 4 + 8` not a multiple of eight**, so the next allocation rounds DOWN
*into the block just written* and its tag lands on that block's first field. The
reservation is now rounded up:

```
end = aligned + ((TAG_BYTES + size + 7) & -8)
```

and the one remaining failure was a test asserting `before + 8` for a record's slot —
**correct before, stale now**, because the slot is the record plus its tag. It is written
as the expression rather than as `16`, so changing the tag or the alignment shows up
there instead of in a number nobody can read.

**The tag is a prefix, so nothing that reads a block had to move.** The length is still at
`base`, the capacity at `base+4`, the elements at `base+8`, a closure's thunk at `base+0`
and its capture count at `base+4`. `readCString`, `writeList`, `emitElementAddress` and
the growth of `push` are untouched — **and the test suite is what proves it**: a layout
change that had moved a reader would have moved a hundred of the 1006.

Two tests land with it. The one that matters **finds the block by its BYTES** and reads
the word four before it, because the tags are 1, 2, 3 and 4 and those are also plausible
lengths — a scan for the tag value would have asserted something true for the wrong
reason. And the other one checks that a block **the host wrote by hand, with no tag,
still works**, because that is what every test helper in this file does.

**Nothing reads the tag yet.** That is the next piece: `"x" + n` can finally tell a number
from a string at run time, which is the question 33 of the 50 corpus programs are waiting
on, and `typeof` becomes answerable with the same word.

### BUG-WASM-79 — `%` was compiled as `+` (closed)

Found by the probe that was supposed to answer a different question. The plan for
`String(n)` needs a **digit**, a digit needs a remainder, and the first thing to measure
was whether the language has a remainder at all. It does — **and it is a different
operation from what it looks like**:

```
 37 % 10  = 47      (37 + 10)         10 % 3   = 13    (10 + 3)
100 % 7   = 107                     5 % 2    = 7      (5 + 2)
  1 % 1   = 2                      37 - 10  = 27  ✓    37 * 10 = 370  ✓   37 / 10 = 3.7  ✓
```

**A missing case and a `default` that hides it.** `getBinOpcode`'s f64 branch lists
`+ - * /` and the comparisons and the logical and bitwise operators, then
`default: return OP.f64_add`. There is no `case "%"` — and **WebAssembly has no `f64.rem`
at all**, because remainder is an integer opcode. So every `%` in this language, where
every number is an f64, fell through to the one opcode the default was already using.

**The fix is a four-opcode sequence**, three of which already existed:

```
f64.trunc → i32.trunc_f64_s → i32.rem_s → f64.convert_i32_s
```

and that is also exactly what JavaScript's `%` is — a **truncating** remainder with the
sign of the dividend: `-37 % 10` is -7 and `37 % -10` is 7, both of which are tests,
because that is the part a remainder that is "close enough" gets wrong.

**It took three attempts and the engine named the mistake each time**, which is the only
reason it did:

1. converted only the divisor → `i32.rem_s` type error, because the dividend beneath it
   was still an f64;
2. spilled the divisor with `local.tee` → `f64.trunc` landed on the divisor's **i32**
   instead of the dividend's f64, because **a `tee` leaves a copy UNDER the value it
   copies**, so the top is never the thing underneath it;
3. two `local.set`s, one per side, and it validated and ran.

**And the table had a second wrong opcode next to it**: `i32_trunc_f64_u` was 0xad, which
is `i64.extend_i32_u`; it is 0xab. Nothing calls it today, and that is the only reason it
has never been caught. The two `reinterpret` entries are fiction — the comment beside
them already says `i32.reinterpret_f64` does not exist — and they are left alone, because
renaming a fiction is not a fix.

**What made this one findable at all** is that the plan called for a digit and the digit
called for a remainder. **An operator is worth measuring when something else needs it**,
and `%` had been in the grammar, in the JS emitter, and in the i32 table the whole time,
correct on one of its two type paths.

### What IS verified about the tag, and the sixth wrong mechanism

The next turn checked the one thing that had never been checked: **what the tag word
actually received at each allocation site**. `emitAlloc` takes a fifth `kind` argument, and
there is a reading of the call sites in which four of five pass only four arguments and the
tag is garbage. **That reading is wrong, and measuring it says the tags are right:**

```
a list             block at 65540: [3][8]   word before: 2   ✓
a string made by + block at 65540: [5][5]   word before: 1   ✓
```

So the reasoning that nearly became a sixth entry — *"`kind` is `undefined` at four call
sites, so a garbage tag is written, which is worse than no tag"* — was **false**, and it was
false because it came from a `grep` of a call site read before the change rather than from
the file. The `kind` IS passed, and a block's tag is what its constructor says.

**That is the real lesson of this stretch, and it is not about the tag.** Six mechanisms in
six turns, every one of them plausible, every one of them wrong, and **all six were
produced the same way: reasoning about what the code must do instead of running it.** The
one measurement in this whole entry — the table above — settles in one run a question that
six explanations had failed to.

without is worth nothing.** `allocblock` is still unexplained, and the next move is
another one of those tables: bisect the emitting FUNCTION, one instruction at a time, and
write down what each removal changes. Six guesses is the argument for the seventh thing
being a table.

#### The table, and the answer: `allocblock` was never an allocation

Two more measurements, from outside the emitter, both cheap:

```
a list, works          functions = 1     ran
a record, works        functions = 1     ran
allocblock, fails      functions = 3     null function or function signature mismatch
```

**`functions = 3` for a program that declares one function** — and that number comes from
the descriptor, not from a byte walk. The control settles it:

```
allocblock, unrecognised     functions = 3   null function or function signature mismatch
storebyte,  unrecognised     functions = 3   null function or function signature mismatch
a call to nothing at all     functions = 3   null function or function signature mismatch
a real helper, for contrast  functions = 1   ran
```

**`null function or function signature mismatch` in this compiler means a call to
something that is NOT THERE.** It is not about types, and six mechanisms were written about
types: the stack, the allocator, the value-sized path, the tag, the void shape. **None of
them was involved, because the allocation never happened** — `allocblock` was lowered as
a call to a function that does not exist, and everything measured afterwards was the
measurement of a missing symbol.

**And that is worth far more than the primitive.** BUG-WASM-45 said *a silent zero is a
refusal with a name*, and BUG-WASM-58 made ten expression forms refuse with a name. **A
call to a callee that does not exist is not one of them**: the program compiles, the module
validates, and the failure is a trap at run time that names the function's signature. That
is the same class of hole, in the most-used form the language has, and it is a small
lowering check: a callee that is an `Identifier` and is neither a parameter nor a known
function should be refused with its name.

**The name of the error is the lesson.** It says "function signature", so every one of the
six readings went looking for a type disagreement. It never said "function not found",
because in WebAssembly's terms a bad index IS a bad signature at the call site. **Read
what the message would have to be true of, not what it sounds like.**

---

**And the answer, measured. It is not `arrayNames`, and it is not the parameter.**

```
  // the seed asked for
  lowerFunction(…, { s: "address", p: "address" }, …)

  // and the module's own table says
  mod.arrayKinds: {"p":"number"}

  fn __probe  params ["i32","i32"]  results ["f64"]
  // `s` is not in the table at all, and `p` is a NUMBER
```

**The seed was OVERWRITTEN before anyone read it.** `listNamesOf` runs over the
helper's body and, for every name it cannot prove is a list of RECORDS, records
`"number"` — and it cannot prove it here, because the body is `p.length` and `p[i]`
with no object literal to learn from. So the seed says *address*, the scan says
*number*, and the scan is written last.

**That also explains why the `arrayNames` fix was inert.** My filter added the
parameters whose `mod.arrayKinds[name]` is `"address"` — and by then `p` says
`"number"` and `s` is absent, so there was nothing for the filter to add. **The fix
was correct about the set and blind to what the set was being fed.**

---

**So the actual rule, in one sentence: a name the LOWERING seeded must not be
re-typed by the body scan.** The scan exists to learn what the source does not say;
the seed exists to say what the source cannot. Whichever runs last wins, and today
that is the one that knows less.

**Which is the same shape as the receiver, the constant, the capture and the
parameter — and this time both facts are in the SAME FILE, one pass apart.**

```ts
for (const name of listNamesOf(fn.body ?? [])) {
  if (!b.arrays.has(name)) b.arrays.set(name, "number");   // ← the guard is on has()
}
for (const [name, kind] of Object.entries(seedLists)) {
  b.arrays.set(name, kind);
}
```

There is already a guard against overwriting — `if (!b.arrays.has(name))` — and it is
on the WRONG side. It stops the scan from overwriting a name the scan itself set, and
does nothing about a name the SEED set, because the seed has not run yet or its entry
is not in the table the guard reads. **The guard is aimed at the wrong writer.**

**What to check first, and it is one comparison:** does `b.arrays` already carry the
seed at the moment `listNamesOf` runs? If it does not, the seed has to be applied
FIRST and the scan second. If it does, the scan needs to be told that a seeded name is
settled, the way the emitter's own `addressNames` settles one.

**And the `endsWith`/`includes` invalid modules fit this too**: `s.length - n` and
`start + i` are arithmetic on a value the scan believes is a number, so the helper's
stack discipline is decided by a type that was never true. One wrong fact, two
symptoms — a comparison that always answers 0 and a module that will not validate.

---

**Which makes this bigger than strings.** The list helpers take a list PARAMETER too —
`map`, `indexOf`, `filter` all receive their receiver as a seed — so whatever covers
this covers them, and this is a fact about **how a seeded parameter crosses into the
module analysis**, not about a language feature. It is the same shape as every other
one in this file:

- a capture that had to be threaded across a function boundary (BUG-WASM-35)
- a constant that had to be materialised across a MODULE boundary (BUG-WASM-45)
- a receiver that had to be passed as an argument (BUG-WASM-54)
- and now a seeded parameter that has to cross into a DIFFERENT analysis

**A fact established on one side of a boundary is not a fact on the other, and each

---

**The methods are reverted, and the reason is the same one as always: `startsWith`

**Which is the sharpest version of the lesson the gate has taught this session.** The

### BUG-WASM-19 — the corpus needs a real exception mechanism (fixed)

**Closed.** `try`/`catch` and `throw` work, including a throw from a helper two
calls deep, caught by a `try` in a different function — which is the only shape
the corpus has.

**Why it could not be a local flag.** Measured: the corpus has **56 `try` (54 with
a catch, 2 with a catch and a `finally`) and 26 `throw`, and not one `throw` is
inside a `try`**. Every throw is in a helper that a `try` in another function
calls, so the failure has to travel.

**The mechanism is one address.** `EXCEPTION_SLOT` sits in the data image right
after the bump pointer. `throw` stores the value there; **every call site**
checks it and returns early if set; a `try` clears it, runs its body, and
branches to the catch when it came back set.

**Four things it took, and the first two are the ones worth keeping:**

- **A call inside a `try` body must NOT propagate.** Leaving the function skips
  the very `catch` waiting for it. Only the lowering knows that, so the call
  carries `inTry` and the emitter reads it.
- **A `return` inside a `try` body must go out THROUGH the slot test.** The
  expression being returned is exactly what may throw, and returning from the
  body never checks. It jumps to a trampoline holding the test, and the merge
  block returns. The same is true of a `throw` inside the body.
- `tryBlock` and `catchBlock` are the **statement arrays themselves**, not
  objects with a `body`. Reading `tryBlock.body` gave `undefined`, `?? []`
  iterated nothing, and **both bodies vanished** — which read as "the return is
  unreachable" rather than as a missing field. A construct that lowers to
  nothing looks exactly like dead code.
- The data image has to cover the slot, or a `throw` writes past its own data
  section and the engine discards it: a throw that silently does nothing.

**What it costs, measured and not hidden.** Every call site now carries a load,
a compare and a conditional branch. The emitted code is materially bigger and
the corpus scan went from about a second to several minutes. That is the price of
a throw that happens in a callee, and it is worth paying only while it is true —
the obvious follow-up is to stop emitting the check in functions that cannot
throw, and that means knowing which.

**Still open:** `finally` runs on both paths, and this backend has no block that
is emitted on the way OUT of an `if`. Running it only on the happy path would be
a different program from the one written, so it is reported instead of guessed.

### BUG-WASM-17 — a program of thirty files became thirty modules (fixed)

**Closed.** `linkProgram` resolves a program's imports, lowers every file, and
merges them into ONE wasm module. Six tests, and the three that run actually
execute: a function imported from another file, a constant exported by another, two
files that both declare `n`, a three-file chain, and the two ways an import can be
wrong.

**Why this shape.** A wasm module has no module system, so the alternative was one
module per file with no way to call across. Names are prefixed per file — two files
may both export `compile`, and the emitter resolves a callee by NAME through one
flat list, so the prefix is what keeps that list unambiguous. The corpus justifies
it: 76 of its 79 imports point at another `.no` file, 2 at a Node builtin and 1 at
an npm package.

**Three things it took, none of them about linking:**

1. **A `VariableDeclaration` carries ONE `name` in Nodeon**, not an array of
   declarators — that is the ESTree shape, and reaching for it meant
   `export const K = 7` was never recognised as something the file owned, so the
   import on the other side looked for a name that did not exist.
2. **A top-level binding's name is a plain field, not a reference value.** The
   rename walked `{kind:"ref"}` operands and never saw `declare.name`, so the
   definition kept its bare name while every use of it was rewritten. Half the
   merge is invisible to a walk that only looks at values.
3. **The lowering decides "direct call" by whether the callee names a function of
   the SAME file — and it runs before the imports are resolved.** So `twice(n)` in
   the importing file was marked indirect, and an indirect call wants an i32 VALUE
   where a name was. The linker is the first place that knows the answer, so it
   re-decides: a call whose renamed callee is a function of the merged module is
   direct.

**The gate now measures PROGRAMS, not files.** It did, and the difference was
everything: a file-by-file measurement said a backend without a linker could reach
exactly one file, which was true and said nothing about a backend with one.

```
files 50 · valid 7 · invalid 3 · parse 11 · diagnostics 29 · threw 0
  13  TryCatchStatement
   6  ClassDeclaration
   4  SwitchStatement
```

**And a distinction worth keeping:** the compiler REFUSING an unsupported program
is a reported gap; the compiler CRASHING is a defect. Letting `compileIRToWasmBinary`
throw made 29 files report as "threw" when the truth was "uses try/catch". The gate
asserts only the second.

**Still open:** a Node builtin or an npm package has no host to ask in a wasm
module, so those imports are reported and not linked. 3 of the 50 files.

### BUG-WASM-16 — a module-level constant had nowhere to live (fixed)

**Closed.** `const K = 7` at the top level read back as its default, so
`fn run() { return K }` answered **0**.

`mod.globals` is a flat instruction list that **nothing executes** — the emitter
has no entry function to put it in, and a wasm function is the only thing in this
backend that can hold a value with a name and a place in the module. So a
module-level constant became a **function**, and every mention of the name became
a call to it. That is also what makes it visible ACROSS files, which is what the
program linker needs and what a per-file instruction list never could do.

**It went in the wrong layer first, and two existing tests said so.** Hoisting
inside `lowerToIR` turned `const x = 1` into a function called `__const_x` — and
`lowerToIR` does not only feed the WebAssembly backend: there is also an
IR-back-to-JS emitter, and its output is a *different program*. Two tests in
`e2e.test.ts` failed and both were right.

**Un IR es un contrato con todos sus consumidores, no un cuaderno privado de
uno.** A rewrite that changes the meaning of a construct belongs to the consumer
that needs it; doing it in the shared pass silently changed another one. The
hoist now lives in `compileIRToWasmDesc`, and the comment there says why.

**One more thing the rewrite had to cover:** a constant used as a `return` value
lives in the block's TERMINATOR, not in its instruction list. Rewriting only the
instructions left the one reference that mattered, and the answer stayed 0 —
which looks exactly like the hoisting not having happened at all.

### BUG-WASM-15 — `export fn` produced no function at all (fixed)

**Closed, and it moved the coverage from 1 of 50 files to 9.**

`export fn f() { … }` is an `ExportDeclaration` **wrapping** a function, and
`export fn` — `fn`, not `function` — is how the entire corpus declares one.
`lowerToIR` looked only for a top-level `FunctionDeclaration`, so every exported
function was **skipped**: the module compiled, validated, and contained nothing.
A call to one then resolved to nothing, which the emitter now reports instead of
dropping.

The unwrapping is one `innerOf` at the top of `lowerToIR`, and it is also what
made `export const K = 7` a module-level value rather than an unsupported
statement. Two things the corpus uses everywhere, both invisible.

**The coverage went from 1 valid to 9**, and the gap list changed shape entirely:

| before | after |
|---|---|
| 32 `ImportDeclaration` | — gone |
| 12 `ExportDeclaration` | — gone |
| 3 `ClassDeclaration` | 11 `ClassDeclaration` |
| 1 `SwitchStatement` | 5 `SwitchStatement` |
| 1 `DoWhileStatement` | 1 `DoWhileStatement` |
| | **15 `TryCatchStatement`** |
| | 2 `FunctionDeclaration` |
| | 1 `ContinueStatement`, 1 `ThrowStatement` |

What is left is no longer module plumbing. It is **language**: try/catch, classes,
switch. Those are features, with a design each, rather than a missing mechanism.

**Still open, and named:** a top-level `const` lands in `mod.globals` and the
emitter never emits them — there is no entry function to put them in, so the
binding reads as its default and the answer is 0. A module-level constant needs a
real slot, and the same piece has to make it visible ACROSS files. Two
`FunctionDeclaration` diagnostics remain too: a function reaching
`lowerStatement`'s default as a statement rather than as a declaration.

### The program linker: designed and measured, not landed

Before writing it, the corpus was asked **what its imports actually import**:

```
  76  relative-no     ← another .no file
   2  builtin
   1  package
```

That is the opposite of what I expected and it changed the work: **76 of 79
imports point at another Nodeon file.** A backend that links Nodeon files reaches
almost all of the corpus, so the linker is the right next piece.

A linker was built and it worked structurally — two files linked, functions
renamed per file (`main::run`, `lib::twice`), the import resolved, the module
**valid** — and then it threw at run time, because a top-level `const` in one file
is not visible in another. Fixing that needs a module-level slot with a getter per
constant, and it is the same piece as the `mod.globals` gap above.

It was taken back rather than landed, for the reason the last two attempts were:
a linker that links and then traps is worse than no linker, and the honest state is
a design with its inputs measured.

### BUG-WASM-13 — closures (fixed)

**Closed.** A lambda that reads a name from the scope around it is a CLOSURE,
and the WebAssembly backend now makes one.

The shape:

1. A lambda that captures `a` and `b` is compiled as `fn __lambda0(a, b, v)` —
   the captures become LEADING parameters. That is all a closure is.
2. A function VALUE is the address of a **closure record with a fixed header**:
   `[thunkIndex: i32][captureCount: i32][captures…]`, one 8-byte slot each. The
   value is the record's address, and the call site reads word 0 for the index.
3. Two blocks of thunks: the plain ones at `realCount + i`, the closure ones at
   `2*realCount + i`. A captureless function's record lives in the STATIC image —
   it never changes, so every reference shares one.
4. The uniform signature gains the record in front, so the closure's own thunk
   can read the captures out of it.

**Measured, and it works:**

| Nodeon | answer |
|---|---|
| `const k = 10; g = fn(v) { return v + k }; g(5)` | 15 |
| two captures, `v * a + b` | 34 |
| three captures, `v * a + b * c` | 16 |
| a captured record, `o.v + x` | 10 |
| the capture outliving the scope it was made in | 20 |
| two closures with different captures | 33 |
| a closure over two arguments | 11 |
| `[1,2].map(fn(v) { return v + k })` | 45 |

**Two attempts got here, and the measurements of the failed one are the useful
part.** A tag in the low bit of the function value — `index * 2` plain,
`address * 2 + 1` for a closure — ran and returned something out of the record
instead of the callee's result in every capture case, while breaking the plain
one. The fixed header replaced it, and then it got to five of nine.

**The defect that stayed until last, and why it hid:** a closure's captured
values are looked up by the **caller's argument position**, not by their index in
the declaration. `__lambda0(a, b, v)` declares `v` third, but the caller's first
argument lands in slot 0 — so reading slot 2 read a PADDING slot, `v` arrived as
0, and `v * a + b` answered with `b`. **One capture hides it entirely**: with a
single capture the declared index and the argument position coincide, so every
one-capture test passed and the bug only appeared at two.

That is worth keeping as a rule: *an off-by-one in a fixed arity that another
parameter can absorb is invisible until the arity crosses the boundary it
absorbs at.* A test with one element proves nothing about two.

**Also learned, the hard way:** a revert that removes a function but leaves its
constant behind compiles until the duplicate name is reached, and a
`String.replaceAll` chain that rewrites `8`→`9` and then `9`→`10` rewrites the
result of the first one too. Both cost a cycle, and both are the kind of thing a
backup copy turns from a diagnosis into an undo.

### BUG-WASM-12 — strings are addresses and nothing more (open, measured)

A string literal compiles to its ADDRESS in linear memory, and no operation on
strings exists. Measured against the JS backend, on the same source:

| Nodeon | JS | WASM | |
|---|---|---|---|
| `"ab" == "ab"` | `true` | `1` | right, for the wrong reason |
| `"ab" == "cd"` | `false` | `0` | right, for the wrong reason |
| `"abc".length` | `3` | `6513249` | reads the record slot named `length` |
| `"ab" + "cd"` | `"abcd"` | `24` | numeric addition of two addresses |
| `("ab" + "cd").length` | `4` | `0` | and then the length of that |
| `["ab","cd"].length` | `2` | `2` | right — a list, not a string |

**The two comparisons are the dangerous ones.** Identical literals are interned
to the same address and different literals to different addresses, so `==` on two
LITERALS is accidentally correct. It stops the moment either side is computed: a
concatenated string, a field, a list element or a parameter compares as a number.
A test written with two literals would pass and tell you nothing.

**And the measurement that matters most is the one that came out RIGHT.** A
`switch` on a string read from a record field works, and it works for exactly one
reason: `==` is pointer equality, and both sides are interned literals.

```
switch o.type { case "FunctionDeclaration" { return 10 } ... }     → 10, 20, 30  ✓
switch t     { case 0            { t = 1 } ... }                   → 1            ✓
let s = "ab"  if n == 1 { s = "ab" }  if s == "ab"                 → 1            ✓ (accidental)
s[i]                                                               → 0, want 'b'
```

So the 31 `switch` statements in the corpus — 383 cases, the backbone of the
self-hosted compiler — are green **on top of** a string implementation that cannot
length a string, index one, or concatenate two. **`switch` working is not evidence
that strings work**, and the two facts have to be kept apart: the first is a real
capability, the second is a coincidence about where string values come from. A
`switch` on a computed string — `"a" + "b"`, a parameter, anything built at run
time — takes the false branch, and nothing in the corpus does it, so nothing fails.

`"abc".length` is worse than wrong — it is a different kind of wrong. `.length` is
the length header of a list, and the lowering had no reason to know that a string
was not one, so it read the record layout's slot for a field called `length` and
answered a denormal double.

**A decision that has to be made before writing a line of it:** what does `s[i]`
mean, a byte or a character? The JS backend says a character, so a WASM backend
answering a byte diverges from the reference for every non-ASCII string, and
`.length` diverges with it. UTF-8 makes them equal for ASCII and different
beyond it, which is the worst kind of difference: right in the examples, wrong
in production. Choosing byte semantics is defensible and is what Go does, but it
is a decision about the LANGUAGE and not a backend detail, so it is not one to
take silently in a compiler. Declaring the type, or a `bytes`/`text` pair, closes
it; until then the honest state is a table like the one above.

The operations themselves — `__slen`, `__streq`, `__sadd` — are mechanical once
the semantics are fixed, and they can be written in the language itself the way
`map` is.

### BUG-WASM-11 — `a.map(fn(v) { … })` had no runtime to live in (fixed)

**Closed.** `map`, `filter`, `foreach`, `sum` and `count` work, and lambdas work.

**The methods are written in Nodeon.** `ir-lower.ts` holds them as source —
`__map_number_number` really is

```no
fn __map_number_number(list, f) {
  const out = []
  for i in 0..(list.length - 1) { out.push(f(list[i])) }
  return out
}
```

— parsed by the real parser and lowered through the real path. A method written
in the language is fixed by the same fixes as everything else, and it reads as
the method it implements. The alternative, emitting its bytecode by hand, would
have been a second implementation of lists that drifts from the first.

**A lambda is LIFTED to a module function.** A function value is an index, and
an index only exists for a function in the module, so `fn(v) { … }` in
expression position becomes `__lambda0` plus a reference to it. A lambda inside a
lambda keeps lifting while the lowering runs, so the list is drained until it
stops growing.

**A capture is reported, not guessed.** A lambda that reads a name from the
scope around it is a closure, and a lifted function shares none of that scope.
Rather than generate one that quietly reads a global of the same name and
returns a plausible wrong number, the names are collected and the compile
refuses. `compileIRToWasmBinary` throws, so the program stops with a reason
instead of running wrong.

**Three defects that made the first attempt answer 0,** and all three were the
same mistake in different clothes — looking a name up where it is not:

1. `fnvalue` resolved the function name against the functions compiled SO FAR.
   A lambda declared third was not there yet, the index came out -1, and the
   value became 0.
2. The direct `call` did the same, and worse: a call with no target was
   **silently dropped** and the destination kept its default. So a list method
   built for the FIRST module that used it worked, and every later module
   answered 0. The helper cache had to hand the function to every module, not
   just return its name.
3. `xs.length` on a PARAMETER was a field read. The lowering only knew a name
   was a list if it had seen it declared from a list literal, and a parameter
   never had been — so it read a record slot and answered a denormal double, and
   every range loop over that list then ran zero times. The fix is general, not
   specific to the methods: a function body says which names it treats as lists,
   by how it uses them.

**A method is built once per PAIR of element kinds** — what the source holds and
what the result holds. `map` over numbers stores an f64 slot and `map` over
records an i32 address; one shared helper had to pick, and the mismatch was not a
wrong answer but an INVALID MODULE (`local.set[0] expected type f64, found
i32.sub`). The result kind comes from the LAMBDA's body, which is visible at the
call site — `records.map(fn(o) { return o.v })` turns records into numbers, and
tying the result to the INPUT got that backwards.

**Still open, with the reason written down:**

- **Closures.** A lambda that captures needs its environment carried with it. A
  thunk carries arguments and nothing else, so a real closure needs a different
  calling convention — an environment pointer in a reserved argument slot, or a
  closure record. It is the biggest remaining piece of the runtime.
- **`map` that returns records it did not build** (`fn(o) { return o }`) is read
  as numbers, and so is a NAMED function's result, whose body is not at the call
  site. Declaring the result type, or tagging every element, closes it.
- **`let x = 0` followed by a line starting with `[`** parses as an index, the
  same automatic-semicolon-insertion trap JavaScript has. Worth a diagnostic
  before it is worth a fix.

### BUG-WASM-10 — a function could not be used as a value (fixed)

**Closed.** `apply(twice, 21)` compiled, validated, ran, and
answered `0`. Three separate things were missing, and each had to be right
before any of them showed:

1. **Materialising a name.** A function name in expression position produced no
   instruction at all, so the argument was nothing. It is now a `fnvalue`.
2. **A type to call through.** `call_indirect` demands a type, and at an
   indirect call the callee is not known. So every function that can be reached
   through a value also gets a **thunk** with one fixed signature, and the call
   goes through that. The thunks are only built when a module actually has a
   function value, so a module of direct calls carries no table and no element
   segment and is exactly the size it was.
3. **A table to call through.** The encoder had no table section and no element
   section at all.

**The design decision worth keeping: pass everything twice.** The uniform
signature takes four arguments as i32 AND the same four as f64, and returns the
result as i32 AND as f64. Each side takes the copy it declared. The obvious
alternative — pass f64 only, and let the thunk convert — would send every
number through `i32.trunc_f64_s` and lose anything above 2^31 or with a
fractional part. `apply(half, 1)` has to answer `0.5`, and it does.

**Four defects of my own, all found by running the code rather than reading it:**

- `functions.push(...)` inside `for (let i = 0; i < functions.length; i++)`:
  the array being walked grows, so the bound never stops. The suite died with a
  4 GB heap.
- I invented a JSON format for the shared type list while the encoder
  deserialises `params=>results`. The uniform type came out with the wrong
  parameter count and the engine said "not enough arguments on the stack" about
  a call that had pushed exactly the right nine. `serializeType` is exported
  now, so there is one format.
- `OP.f64_convert_i32_u` was not in the table. `undefined` reached the encoder,
  was coerced to `0`, and `0` is the `unreachable` opcode — so a typo in an
  opcode NAME became a trap at run time pointing at nothing. The encoder now
  refuses any byte that is not a real byte. The value that got through the guard
  was `0xb9`, which is `f64.convert_i64_s`.
- A thunk pushed four arguments whatever the callee declared, so the extras sat
  on the stack and were read as the callee's first parameters.

**Still open:**

- **A lambda in expression position** lowers to a placeholder string. Lifting it
  to a module-level function is the small half; the large half is the closure,
  because a thunk carries arguments and no captured environment. This is the
  blocker for `map`/`filter` as written in the language people expect.
- **A function value reaches a function with more than four parameters** with
  the extra arguments lost. Four covers the standard list methods; the limit is
  declared, not accidental.
- An indirect call returns both representations and the CALLER picks by its own
  static expectation, which at an indirect call is a guess. A saturating
  conversion keeps it from trapping; a type confusion is still possible, and that
  is inherent to an untyped indirect call.

### BUG-WASM-9 — a list read through a field lost its element kind (fixed)

**Closed.** The lowering records whether a list holds numbers or record
addresses, but only for a list literal and the binding it is assigned to. It
does not record it for **the temporary a field read produced**, and that
temporary is the name every later read uses:

```no
fn g() { const o = { items: [{ v: 3 }] }\n return o.items[0].v }   // answered 0
```

The element was read with `f64.load` instead of `i32.load`, so the record
address became a double and `.v` read from nonsense. The module analysis now
carries the element kind across fields, bindings and call arguments, and
`isAddressArrayValue` is the single place that asks — it used to be written out
three times, each copy consulting only the lowering.

It is the same bug as `.length` on a field (BUG-WASM-7 item 4), one level
down: a value read out of a record had lost the type the module already knew.

**Also closed by the same work:** the skip for "objects as values inside an array
of mixed types" was stale — arrays of records worked once the allocator existed.
What does NOT work is a list that genuinely mixes numbers and records, because
a list has ONE element width. That stays a skip, with the reason written down:
boxing every element in a tagged cell fixes it and costs an indirection on every
access, which is a decision about the data model rather than a patch.

### BUMP-WASM-8 — the heap grows, but is never reclaimed (partly closed)

The heap is a bump pointer with **no collection**. A game loop that builds a
grid per tick spends `8 + rows*cols*8` bytes a tick, and nothing is ever
returned.

**Half of it is fixed: the allocator grows the memory.** `MEMORY_PAGES` (16) is
now the memory the module *starts* with, not a ceiling — `emitAlloc` calls
`memory.grow` when an allocation would not fit, and traps at the allocation if
the grow cannot be satisfied.

This was worth doing on its own because the failure it removes is a **bad
diagnostic**, not a wrong answer. A wasm access past the end of memory traps,
so the program stops — but the message is `memory access out of bounds` pointing
at a load or a store in whatever line of compiled code happened to run out. It
says nothing about the real cause, which is that the program needs more room.

> An earlier note in this file claimed such accesses were "discarded silently".
> That was wrong, and it was wrong in the direction that made the bug look
> scarier than it is. Measured: disabling the grow makes the growth test fail
> with `RuntimeError: memory access out of bounds`, not with wrong numbers. The
> claim was corrected in the code, the test and here.

**Still open: reclamation.** A grid is dead as soon as the reference to it is
dropped, which a bump allocator cannot see. This needs either a mark-and-sweep
pass driven from the wasm locals and the linear stack, or reference counting
threaded through every write — and every write includes the ones this emitter
synthesises, so counting has to be emitted, not bolted on. Until then, a long
loop still grows without bound, just at the engine's ceiling instead of a
compile-time one.

### A note on how these bugs presented

`loadfield` and `storefield` existed in the IR from the start but had **no case in
the emitter**. An instruction the emitter does not recognise is not an error — it
is a silent wrong answer, and `o.x` compiled, validated and ran while returning 0.
A second version of the same: `internArray` was initially called as `intern`, so
the array was written to memory as the ASCII bytes of `"10,20,30"` and every read
returned 0. Both were invisible until the module was executed and its memory read
back. Neither would have been caught by checking that the bytes decode.

A third: `i32.reinterpret_f64` was assumed to exist because the reinterpret
family does. Asking the engine — building a `(f64)->i32` module per opcode in
`0xb8..0xbf` — showed there is no such instruction; the family is f32/i64 only,
and an address in an f64 has to go through `i32.trunc_f64_s`.

### Closed: arrays of records (BUG-WASM-5)

The last gap is closed. An array of records now reads and writes correctly, and
a `for` over records accumulates the right total.

**The bug was a width mismatch.** `storeelement` wrote every element with
`f64.store`, including a record ADDRESS. The matching read used `i32.load`. So
the slot held the *bits of the double* `65536.0`, and the `i32.load` that read it
back saw the low 32 bits — **zero**. Writing and reading the same slot with
different widths is silent: no validation error, no trap, just a wrong answer.
`storeelement` now uses `i32.store` when the array is of addresses and
`f64.store` when it is of numbers, chosen from the same `arrayKinds` the read
uses.

### Four bugs in the allocator, found by decoding bytes (all fixed)

Each looked like a different bug, and none produced an error message:

1. **A signed LEB constant read as a positive one.** `i32.const -8` encodes as
   the single byte `0x78`, and the engine reads `0x78` as **120**. So the
   alignment mask became `x & 120`, which collapses the heap pointer to 0, the
   allocator never advances, and every record reads back as 0. Fixed by never
   encoding a negative constant for a mask: `x - (x & 7)` uses one small
   positive constant that cannot be mis-encoded.
2. **A mask that computed the remainder.** `(x + 7) & 7` keeps only the low
   three bits, so 65543 & 7 is 7, and 7 - 7 is 0 — the record is allocated at
   address 0. Aligning to 8 means *clearing* the low three bits.
3. **The heap was outside the memory.** The data section needs ~65524 bytes, so
   one page was allocated, but the heap starts at 65536. Every store into it was
   out of bounds and **the engine discarded it silently**. The memory must have
   at least two pages whenever the data reaches into the first.
4. **A slot written and read at different widths** (above).

The general lesson: **an out-of-bounds wasm store is a silent no-op, not an
error**, and a slot written at one width and read at another is equally silent.
A backend that "works" on small data and returns zeros on larger data should be
checked against a memory-size assertion and a width assertion.

### Found by a real program: `examples/life.no`

The feature-list tests all passed and the compiler still could not run a real
program. Conway's Life on an 8x8 grid — a record holding a grid, a flat array of
cells, nested loops, a conditional inside a loop, and a function call per cell —
exposed five defects at once, none of which any unit test had been shaped to
catch:

1. **A `declare` bound to a record was never pinned as an address.**
   `inferLocals` pinned `const xs = [...]` (an array) but not `const g = {...}`.
   A record binding stayed a provisional `f64`, so `return g` returned the
   ADDRESS as if it were the value: a function that builds an object came back as
   `65536`, and the program carried on with garbage.
2. **A call was always typed `f64`.** `cells.push(0)` returns the array, an i32
   address, and storing it in an f64 slot made the engine reject the module:
   `local.set[0] expected type f64, found call of type i32`. A call is now typed
   from the callee's own result kind.
3. **A conditional inside a loop lost its test.** The loop body was emitted
   linearly, so a nested `if` had its instructions inlined with no `if` at all:
   `if i == 2 { n = n + 1 }` ran on EVERY iteration, and a 5-iteration loop
   returned 6 instead of 1.
4. **A nested loop never advanced and hung the process.** An inner loop reached
   through a forward jump had no `loop` construct and no back edge. The fix is
   recursive emission — but the first attempt made a loop's own back edge look
   like a nested loop and recursed forever (`Maximum call stack size exceeded`).
   The two cases are distinguished by whether the jump points *at* the loop
   already being emitted.
5. **The `for` range is inclusive and that is not a bug.** `for i in 0..(ticks-1)`
   generated `i <= ticks - 1`, so it ran `ticks` times. The reference
   implementation disagreed with the compiler until both were written to do the
   same thing: the arnés was wrong, not the compiler.

After these, the JS backend matches a hand-written JavaScript reference exactly
on the whole program, and the WASM backend runs the same program up to
`cells.push`, which a linear-memory array has no room for (see the skipped
tests).

The lesson is the one that keeps recurring here: **a suite of feature tests
answers "does this case work", never "does a program work".** A grid, a loop and a
call in one file found five bugs that 56 passing assertions did not.



Five of my own measurements produced confident, wrong conclusions across these
rounds. The last one is the most instructive:

- I read an array slot with `getInt32(16)` and concluded the write had not
  happened. The slot holds `65536.0` as an f64; its low 32 bits are `0`, so the
  value was *correct* and my reader was wrong. Reading an f64 as an i32 looks
  exactly like a value that was never written.
- A `DataView` built with a hand-computed byte offset over a `Uint8Array`
  subarray reported slots as 0 while the program read them.
- A hand-rolled bytecode decoder reading LEB128 as unsigned turned `-8` into
  `120` and `i32.and` into "op71".

Each looked like a compiler bug and sent me after the wrong layer for several
iterations. **Read the value with the type the compiler used to write it, and
build the reader with the same library that writes the format.**

### BUG-WASM-6 — `array.push` and indexed assignment (fixed)

**Closed.** `a.push(x)` and `a[i] = v` both work. The array header is
`[len][cap][elements]` with capacity rounded up to a power of two (minimum 8),
and both lower to their own instructions — `arraypush` and `storeelement` —
because this backend has no runtime to dispatch a method, and `a.push` as a
field access was loading a field named "push", which does not exist.

Getting there took three defects that all presented as "the module validates
but the answer is 0":

1. **The capacity was read from the wrong address.** `i32.const 4; i32.load`
   pushes the *address* 4; the memarg's offset has to carry it. With offset 0
   the load returned the LENGTH, so `len < len` was always false and the store
   never ran. The capacity word is read with the memarg's offset.
2. **The header store pushed value before address.** `i32.store` pops the value
   from the top and the address beneath, so the stack must be `[address,
   value]`. Written the other way round, the store wrote to address `len+1`
   instead of the header.
3. **An indexed assignment was dropped entirely by the lowering.** `a[0] = 9`
   evaluated the right-hand side, emitted an `exprstmt` and moved on: the array
   was never written. It compiled, ran and returned the untouched value.

The third one is why the whole program was 0. Every cell the game writes goes
through `next.cells[i] = alive`, so nothing was ever stored.

**Growth past the initial capacity: fixed.** See BUG-WASM-7.

### BUG-WASM-7 — `examples/life.no` ran six different ways (fixed)

**Closed.** The game now runs in the WASM backend and gives the same answers as
the JS backend and as a hand-written JavaScript reference, for 1, 2, 3, 4, 8 and
16 ticks. Before this, the program did not even compile there.

The lesson is the shape of the failure. Every feature-level test passed at every
point below. Six defects were sitting behind a green suite, and each presented as
something other than itself:

1. **A `push` past the block's capacity DROPPED the value.** `makeGrid(8, 8)` is
   64 pushes and a fresh list holds 8, so the game never had a grid. The block is
   now grown in place: allocate `cap*2` slots, `memory.copy` the elements over,
   and write the new address back. The write-back has to reach the *source* of
   the address too — `g.cells.push(x)` re-reads the field on every iteration, so
   updating only the temporary would grow the original block again on the next
   push.
2. **Every `[]` in a program was the SAME list.** Array literals were interned
   into the static data image at a compile-time address, so two evaluations of
   `[]` shared one block and one function's writes appeared in another's list.
   Both lists and records are now bump-allocated per evaluation.
3. **A record field holding an address was written as a double.** `objlit` and
   `storefield` wrote every field with `f64.store`; reading an address back with
   `i32.load` takes the low 32 bits of a double, and those are zero for every
   address in this heap. `g.cells` came back as the null page. The width is a
   property of the FIELD, so it is now decided once for the module.
4. **`.length` on a list was a field read.** It was lowered to `loadfield` and
   given a slot in the record layout like any other name, so the answer was
   whatever bytes sat at that offset — a denormal double where a count belongs.
   The lowering emits `arraylength` when it knows the value is a list, and the
   backend applies the same rule when only it can know: a field the module pushes
   to anywhere is a list everywhere.
5. **The `else` arm of an `if` ran at the wrong time.** The branch terminator's
   `elseLabel` always names the MERGE block, never the else arm — the lowering
   writes `elseLabel: endLabel`, and the else arm gets its own `else_…` label that
   only its position marks. Reading `elseLabel` as the else arm emitted the merge
   block's instructions into the `else` slot and then emitted the real else arm as
   a fall-through. `if c { a = 1 } else { a = 5 }` set `a = 5` when `c` was TRUE
   and left it alone when `c` was false. This is the one that made every Life rule
   wrong at once.
6. **A value's record-ness did not travel across a function boundary.**
   `seedGlider(g)` only ever hands `g` to `place` and returns it, so a per-function
   rule typed it as a number; `simulate`'s `g` is only ever bound to a call. The
   fact crosses functions, and in `simulate` it also travels in a cycle. It is now
   computed once for the whole module and iterated to a fix point.

**Two of my own mistakes inside the fix, both caught by running the code:**

- I used sub-opcode `11` for `memory.copy`; that is `memory.fill`, which takes
  (dest, value, size). It *validates happily* and fills the grown block with a
  repeated byte pattern, so the wrong constant is indistinguishable from a
  memory bug at runtime. `memory.copy` is 10.
- The first version of the module fix point learned that a `declare`/`assign`
  target was an address **without checking its value**, which typed almost every
  name as an address and made `totalAlive` return a pointer.

**Still open (BUMP-WASM-8):** the allocator is a bump pointer with no collection
and no `memory.grow`, so `MEMORY_PAGES` is a ceiling rather than a size. A game
loop that builds a grid per tick consumes `8 + rows*cols*8` bytes each time and
will exhaust a 1 MiB heap after a few hundred ticks. Reclaiming a grid when the
reference dies is the next piece.

### Fixed: a function that returns a PARAMETER record

`fn place(g, r, c, v) { g.cells[…] = v; return g }` receives a record and
returns it, but its wasm result was typed `f64`, so a caller stored a
reinterpreted double where an address belonged.

The decision is now made once for the whole module, in `inferModuleAddressTypes`,
by a fix point rather than per function — see BUG-WASM-7 item 6. The signature,
the local map and the result classification all read that one analysis, so they
cannot disagree. Three copies of the same rule, computed separately, is what let
the signature learn something the body did not.

## Test methodology

The suite asserts on the emitted JavaScript string. That is not enough: a correct
string can come from a wrong AST, and a string assertion never checks that the
program does what it says. `tests/semantics.test.ts` compiles and **runs**
programs across the whole language surface and compares behaviour. Bugs
BUG-012, BUG-013 and BUG-014 were invisible to string assertions and were found
by executing output.

Corollary: when a test fails, first check whether the *test* is wrong. An
execution harness that evaluates its own expectation as JavaScript will report
bogus failures that look like compiler bugs.

## Execution-verified bugs (round 2)

- **BUG-013 — `match` guard spelled `when` was never implemented.** The README

### BUG-WASM-82 — a call to a name that is not bound compiled, validated, and trapped with a message about a SIGNATURE

**CLOSED.** A callee that is a bare `Identifier`, is not a function of the module and has
no slot in the function being lowered, is now refused **by that name**. Four shapes
measured before, none of which said anything:

```
fn run() { return allocblock(8) }   →  no diagnostic · valid module · TRAP
fn run() { return noexiste(1) }     →  no diagnostic · valid module · TRAP
fn run() { return super(1) }        →  no diagnostic · valid module · TRAP   (outside a class)
fn run() { return setTimeout(1) }   →  no diagnostic · valid module · TRAP
```

and the trap was always `null function or function signature mismatch` — the words the
engine uses for calling a function that does not exist. The program WAS doing that, and
the message pointed at a **type**.

The member half was already named, by the emitter: `console.log(1)` refuses with
`una llamada a un miembro ("log") … no hay host al que preguntar`. So the bare name was
the hole, and it is the most ordinary shape the language has: `f(x)`.

**This is the real cause of BUG-WASM-81's symptom.** That entry narrowed `allocblock` to
`emitAlloc`'s value-sized path and never got to check whether the call was real. The call
was not: `lowerExpr` asked one question — "is this identifier a function name?" — and a NO
did not mean *refuse*, it meant *load the local of that name and call through it*.

#### The rule is "the slot does not exist", not "it is not a function"

The obvious rule — reject a callee that is not a function — was **ruled out by a census**
before any code was written (`.mavis-probe/callee.txt`, 386 bare-name callees over 96
files):

```
función declarada: 336     binding: 13     NINGUNO: 48     en varios cestos a la vez: 11
```

Eleven names are in more than one bucket: `resolve` is a binding in one file and unknown in
another; `walk`, `compile`, `buildRoutes`, `wrapHtmlShell`, `matchRoute`, `compileNoFile`
likewise. **The name alone cannot decide what a call means.** So `BlockBuilder` now records
what has a slot — parameters, `declare`, and `assign` — and the refusal asks about the slot.

`assign` counts on purpose and in the **permissive** direction: `f = (v) => …` binds `f`
with an `assign`, and a name wrongly *in* the set is the old behaviour while a name wrongly
*missing* is a working program refused. The registry is filled inside `emit` rather than at
each declaration site, because a variable, a destructured name, a `for` counter, a loop
variable and a `catch` parameter are five sites and a sixth would be forgotten.

#### Seven shapes that must keep working, each with the answer it gave before

A refusal can be bought with a false positive, so the legal shapes are asserted with the
value they produced **before** the change — not with a value written from what the code
looks like it should do (`.mavis-probe/callee2.txt`):

```
declared function 42 · closure in a binding 42 · closure that captures 12
arrow, expression body 42 · function as argument 42 · recursion 120 · nested fn 42
```

All seven still answer, and all seven pass.

#### The first version refused three functions that exist

It fired on imports. `wasm-modules.test.ts` went red naming `twice`, `na`, `nb`, `quad` —
and the reason is structural, not a missing case: **`lowerToIR` lowers ONE file, and the
linker runs afterwards** (`ir-modules.ts:201`). While `f(1)` is being lowered, a name that
came in through `import` is in no function table and in no slot.

An import is a declaration the linker resolves, so it is now seeded into the registry from
the AST, reading **the linker's own shapes** (`namedImports[].alias ?? .name`,
`defaultImport`) rather than restating them — two lists of the same fact drift. An import
that names something the other file does not publish is still not this hole: the linker
validates every import against the file's own exports and says so by name.

### BUG-WASM-83 — `allocblock` and `storebyte`, and a number becomes text (PARTLY)

**The two PRIMITIVES WORK.** Measured, executed, and green in `tests/wasm.test.ts`
under `BUG-WASM-83: allocblock and storebyte`:

```
const b = allocblock(5)   b.length            → 5
const b = allocblock(3)   storebyte × 2, b.charCodeAt(1) → 105
const b = allocblock(6)   read back from memory        → len 6, first byte 0
fn mk() { const b = allocblock(2)  return b }          → valid module, addr 65540, len 2
fn mk(k) { const b = allocblock(k)  return b }         → valid module, addr 65540, len 2
```

**No `i32.add` written by hand.** `allocblock` IS `emitStringBlock` with an empty
piece list — the same allocation, header and NUL as a concatenated block, with
nothing to copy — and the size arrives through the `pushSize` callback `emitAlloc`
has always had for a growing block's capacity. So the two reverted attempts of
BUG-WASM-81 died writing the copy by hand, and neither `emitStringBlock` nor
`emitAlloc` changed. `storebyte` is one `i32.store8` at `block + 8 + index`, which
is the header rule every other read and write of a string byte already uses.

**The header carries the length, so the program writes no NUL and updates no
length** — which is why this shape works where BUG-WASM-81's plan (count digits,
write from the back, write a NUL) was heavier than it needed to be.

`allocblock` takes ONE argument. BUG-WASM-81 wrote `allocblock(b, n)` — a kind and
a size — and the kind has no meaning here: the block is a string block and its own
tag says so. The two-argument form is refused **by name**, because taking the first
argument silently would hand the program a block of the wrong size with no way to
know.

### BUG-WASM-84 — a function with two returns of different kinds, and two rules for one fact

**CLOSED. A number is now text, and the route is two instructions and a loop written in
the language.** The seven skipped cases and their string-method neighbour are green
(`tests/wasm.test.ts`, `BUG-WASM-83: allocblock and storebyte`):

```
0 → "0"    7 → "7"    42 → "42"    100 → "100"
12345 → "12345"    999999 → "999999"    1000000 → "1000000"
numToStr(42).length → 2      numToStr(42).charCodeAt(0) → 52
```

**The defect.** A function's result type was the widest of the types of the values it
returned, and a string **literal**'s type is f64 (`resolveType` → `inferLitType`, and a
string is not a number) while the same string in a local is i32. So a function that
returned a literal on one path and a block on another got the signature `f64` — while
`returnsAddress`, the table the **call site** reads, said `i32`. The engine refused the
module with `local.set[0] expected type i32, found call of type f64`: one word for two
disagreements, because the caller typed the call's result from `returnsAddress` and the
callee's signature was computed without ever asking it.

Ablation, one ingredient at a time (`.mavis-probe/ablate83.txt`) — and **not the digit
loop**: the reduced case has no loop, no `storebyte` and no `Math.floor` in it.

| program | callee signature | caller | before | after |
|---|---|---|---|---|
| block, no parameter | `() => (i32)` | `() => (i32)` | VALID | VALID |
| block + parameter | `(f64) => (i32)` | `() => (i32)` | VALID | VALID |
| block + early `return "ab"` | `() => (f64)` | `() => (i32)` | **REFUSED** | **VALID, `"ab"`** |
| block + parameter + early return | `(f64) => (f64)` | `() => (i32)` | **REFUSED** | **VALID** |
| only a string literal | `() => (f64)` | `() => (f64)` | VALID | VALID |
| string literal + number | `(f64) => (f64)` | `() => (f64)` | VALID | VALID |

**The fix is one line and it is not a new rule.** `inferResultType` asks
`returnsAddress` first: if the module already knows the function gives an address, that
IS its result type. It is the call site's rule applied at the other end of the same fact,
so the two can no longer be written independently.

**And it can only make a module more valid, never less** — which is why it needed no
regression net beyond the suite. Every call site *already* pushed i32 for a function
`returnsAddress` called an address, so a callee whose signature said f64 was a module
the engine already refused. Forcing the signature to match turns an invalid module into
a valid one; there is no program that was accepted and stops being accepted. Measured:
**1033 pass / 44 skip before, 1033 / 44 after** — nothing moved, which is the prediction
holding rather than a coincidence.

#### What this unblocks, and it is bigger than the eight tests

The corpus has **33 programs that interpolate a number into a text** and could not
compile, because a number in a string is a FORMATTING decision that was never taken.
Three separate walls stood in the way, and this removed the last one:

1. no way to reserve memory → `allocblock` (BUG-WASM-83)
2. no way to write a byte → `storebyte` (BUG-WASM-83)
3. no way to return a block from a function → **this**

**The remaining piece is not a compiler feature, it is a library function.** `numToStr`
is twenty lines of Nodeon, and the language already has the exact mechanism for it: the
string methods are Nodeon source templates lowered on first use (`STRING_METHODS` →
`ensureStringMethod`). A `numToStr` built the same way is a *standard library entry*, not
a backend feature — which is the shape the whole language wants: the compiler grows one
primitive at a time, and everything a person actually writes is written in the language
on top of it.

Then `+` with a number and a text is `emitStringBlock` with a third piece, and
`typeof` reads the tag that BUG-WASM-78 already put in front of every block. Both are
now the *easy* half of a wall that was previously the whole of it.

**And the library function above is BUG-WASM-85, below, and it is done** — built by
the same mechanism, on first use, with a program's own `numToStr` taking precedence. The
template half of this is still standing, and it is a *lowering* decision rather than a
formatting one: a hole holding a number becomes an `emitStringBlock` piece whose source is
`numToStr(hole)`. The format question only becomes a question when someone chooses to render
a fraction.

**So the instruction is `emitStringBlock`'s terminator** — `get(fresh); get(total); c8(8); add;
c8(0); i32.store8` — and **at that point `fresh` holds 0**, because the address it writes is

immediately: a layout without its NUL is a product change, and the experiment was never
proposed as the fix.

a single question rather than a search:

| what | verdict |
|---|---|
| `ctx.scratchLocal()` | `ctx.nextLocal++`, a NEW index per call — so `fresh ≠ total` |
| the declared locals of `f` | 9 = 5 named + exactly the 4 scratch locals `allocblock` asks for |
| the local TYPES | `[f64,f64,i32,i32,f64,i32,i32,i32,i32]` — the block is i32 where it should be |
| `emitAlloc`'s last act | `local.set local` with `aligned + 4` — the block address, as documented |
| the allocation's RESULT | 65540, `tag 1`, `len 4`, `cap 4`, bump pointer at 65584 |
| the memory layout | `[tag][len][cap][bytes…][NUL]`, and `readCString` reads the length |

So the store is right, its operands are right, and the value it reads is 0. **The remaining
question is one of provenance: which declared slot is the index `fresh` names, and why is that

shifted index is a bug in how the local list is built, and a clobbered slot is a bug in what
else writes there — and they are told apart by one measurement: a program that allocates

#### CLOSED — the bytes of the tail say it, and the fix is one `i32.add`

Reading the emitted tail is not a disassembler, it is two byte pairs, and it answered the

```
119: 20 05      local.get 5          ← total
121: 41 08      i32.const 8
124: 6a         i32.add              ← ONE add
125: 41 00      i32.const 0
127: 3a 00 00   i32.store8           ← consumes ONE
```

file", and that was wrong: it is a **parameter** of the functions that take a spacing, used
165 times. The same is true of `name`, `label`, `type`, `kind`, `source`, `operator` — the
whole top of the list.

**And a parameter's field is a property of the CALLER.** `fmt(sp)` says nothing about what
`sp` is, because the answer lives in a function that may be in another file. That is the
first thing in this line of work that no amount of per-file analysis can answer, and it is why
the calls were a bug (BUG-WASM-89) and the fields are not.

#### The project already has the machinery, and it is not wired

`bootstrap/compiler/type-checker.ts` is 1381 lines with a complete structural type:

```ts
export type NType =
  | { kind: "primitive"; name: "string" | "number" | "boolean" | "void" | "null" | "undefined" }
  | { kind: "array"; element: NType }
  | { kind: "object"; properties: Map<string, NType>; optional?: Set<string> }
  | { kind: "function"; params: NType[]; returnType: NType; … }
```

**It knows the type of a parameter**, from an annotation or from inference. What it does not
do is ANSWER: `typeCheck(ast)` returns `TypeDiagnostic[]`, and it is optional
(`options.check` in `compile.ts`). There is no `typeOf(node)` to ask.

#### The question, and it decides what Nodeon is

**A. The WASM lowering asks the type checker.** `typeCheck` grows a query API and the
lowering consults it for `x.field`. The cheapest of the two, and it couples a backend to a
pass that is today separate and optional. It also makes the answer depend on whether the
program type-checks at all: for a file with no annotations the answer would be `any`, and
`any` is not a licence to concatenate.

**B. The language says what a function receives.** A parameter carries a type, and
`x.field + "text"` is only accepted where the annotation provides the field's type. The more
expensive one, and the one this project's own argument argues for — a language meant to be
**read by people** should say what its functions take, and `sp` being a `string` is a fact a
reader wants written down rather than inferred three files away.

**The corpus is written in A's dialect** — 304 occurrences of a parameter's field, with no
annotations — so choosing B means the corpus has to grow annotations, and choosing A means the
type checker has to grow an answer. Neither is a bug fix and neither is small, which is why it
is filed as a question rather than attempted.

#### Verified

```
suite       1078 pass · 36 skip · 0 fail
gate        valid 3 · invalid 0 · parse 11 · diagnostics 36 · threw 0
build       45 compiled, 0 failed
```

Nothing changed in the tree for this entry: it is a census and a question.
**The decision, taken and applied: the language ANNOTATES ITS PARAMETERS** —
`fn fmt(spec: Spec)`. Not the type checker answering on demand: what a function receives is
written down, because a language meant to be read should say so rather than infer it three
files away.

**The mechanism is in and the five cases are green**
(`tests/wasm.test.ts`, `BUG-WASM-90: a parameter's annotation, read by the lowering`):

```
interface Spec { sp: string  nl: string }
fn show(spec: Spec) { return "[" + spec.sp + "]" }      →  "[a]"
fn show(spec: { sp: string }) { … }                      →  the inline form works too
interface Count { n: number }
fn show(c: Count) { return "n=" + c.n }                 →  "n=7"
```

**And it needed no new syntax, which the measurement said before the code did.**
`parseParamList` has always read `name: Type` into `Param.typeAnnotation`,
`parseTypeProperty` gives the members of an object type, and the language has interfaces and
type aliases. **The lowering simply never looked** — the third copy of "is this a string",
and the two copies that existed were `receiverIsProvedString` and `isProvedNumberExpr`.

Both directions, because an annotation settles two questions at once: a field declared a
**string** is proved, so the `+` concatenates; a field declared a **number** is wrapped in
`numToStr`, so the `+` renders instead of refusing. With only the first, half the question
would still stop at the refusal.

#### Three pieces, and the third is the one that is easy to forget

1. **`namedTypes`** — the types the file declares, so `fn f(x: Spec)` can be read through a
   name and not only through an inline object.
2. **`paramFields`** — the annotated fields of the parameters of the function being lowered,
   reset per function. Reset ALWAYS: a name in one body says nothing about the same name in
   another, and a stale answer here makes a refusal disappear.
3. **The mark the EMITTER reads.** A field read lowers to a temporary, and `isStringValue`
   asks the emitter's own `stringNames`, a set it derives from the instructions. A mark only
   in the lowering silences the refusal and then the module **fails to VALIDATE** — a worse
   message about the same fact. So the mark goes through `markString`, in both places, and
   the rule is the one BUG-WASM-86 learned the hard way: **two readers, one mark.**

#### And a shape mistake this file has now made twice

`InterfaceProperty.name` is an **Identifier node**, `{ type: "Identifier", name: "sp" }`,
while an inline `{ sp: string }` carries a plain **string**. `String(p.name)` filed every
interface field under the name `[object Object]`, and a named type resolved to an object with
**no fields** — which reads exactly like "the annotation says nothing".

That is the same mistake as BUG-WASM-89's `ReturnStatement.value`, and the lesson is worth
more than either fix: **in an AST a declaration's `name` is a node and an expression's `value`
is a string, and nothing in the type says which is which.** Print the shape before reading it
— `.mavis-probe/annot.probe.ts` is nine lines and it named both shapes in one run.

#### The corpus half, and it is 20 annotations rather than 304 sites

The census, by the parameter a field is read from (`.mavis-probe/fields88.txt`):

```
  225  ctx            campos: sp, nl                     ← THREE QUARTERS of the work
   18  stmt           campos: label, type, kind, source, namespaceImport, defaultImport

```

**`ctx` is a single object threaded through the formatter with two string fields.** One
interface and a handful of annotations is three quarters of this wall, and it is the case an
annotation is most obviously for: the formatter's contract, written down.

## BUG-WASM-91 — una cadena en la posición de verdad: el compilador contesta mal y no lo dice

**Estado: CERRADO por rechazo con nombre.**

Cuatro constructos, un solo error, y los cuatro contestaban **mal en silencio**: módulo válido,
cero diagnósticos, y una cadena que no era la que el programa pedía.

```
  ""  ? "SI" : "NO"   →  "SI"    quería "NO"
  !""                  →  0       quería 1
  "a" || "b"           →  "b"     quería "a"
  "a" ?? "b"           →  ""      quería "a"
```

### La causa, que es una sola

Una cadena es una **dirección i32**, y esa dirección nunca es 0 — tampoco la de la cadena
vacía, que es un bloque de verdad con cabecera de verdad. Así que todo operador que pregunta
«¿esto es verdad?» está preguntando por la **dirección**, y la respuesta siempre es «sí»:

- un `? :` ramifica sobre un valor distinto de cero, así que una condicion vacia toma la rama verdadera
- `!` es `i32.eqz` sobre un valor distinto de cero, así que `!""` es 0
- `||` y `??` están en el `LOGICAL_OPS` del emisor, así que son `i32.or` de dos direcciones

Las direcciones lo demuestran: un `"a"` suelto es 12, `"a" || "b"` devolvió 28 y
`"a" ?? "b"` devolvió 40. **Ninguno de los dos resultados es la dirección de un operando.**

### Por qué cuesta verlo

`&&` y un `? :` cuyas **ramas** son cadenas funcionan bien. La forma parece soportada hasta
el único caso que no lo es, que es la condición.

### Por qué un rechazo y no una implementación

Hacerlo bien es cargar el `u32` de longitud de la cabecera del bloque y compararlo con 0:
trabajo real en el emisor, y no es de este commit. Hasta entonces el rechazo con nombre es la
respuesta honesta, y es lo que la casa del proyecto pide: un hueco se niega **por su nombre**.
Un compilador que contesta `"SI"` para `"" ? "SI" : "NO"` es peor que uno que dice que no lo sabe.

**Solo WASM**, por el motivo de BUG-WASM-77: la bajada es compartida y en JavaScript `""`
realmente es falsy. La puerta está **dentro** del helper, no en las tres llamadas, porque tres
llamadas son exactamente donde una se olvida del destino — y esa puerta tiene un test propio.

### Verificado

```
mutación   revertir el arreglo → 4 tests rojos (de 7 nuevos)
mutación   quitar la puerta forWasm → el test del backend de JavaScript se pone rojo
suite      1090 pass · 36 skip · 0 fail    (1083 antes: los 7 son de estas dos entradas)
puerta     valid 2 · invalid 0 · parse 11 · diagnostics 37 · threw 0
build      45 compiled, 0 failed
```

`valid 3 → 2` es una **mejora**, no una regresión: el fichero que salió de la lista estaba
compilando con respuestas equivocadas. La puerta enseñó por qué — el recuento **sube** cuando
un compilador deja de mentir.

## BUG-WASM-92 — `??` no está implementado: se compila como una suma, en silencio

**Estado: CERRADO por rechazo con nombre.**

Medido sobre números, sin cadenas por medio:

```
  1 ?? 9   →  10    quería 1      y el CONTROL  1 + 9  →  10   (lo mismo)
  9 ?? 1   →  10    quería 9      1 + 9 == 9 + 1, así que los dos son la suma
  0 ?? 9   →  9     quería 9      bien por casualidad
  5 ?? 0   →  5     quería 5      bien por casualidad
```

### La causa

El conjunto `LOGICAL_OPS` del emisor es `["&&", "||", "&", "|", "^", "<<", ">>", ">>>"]`
y **`??` no está en él**, así que `??` llega al `default` de `getBinOpcode`, y ese `default` es
`f64.add`. `1 ?? 9` **es** `1 + 9`.

### Por qué `??` y no también `&&` y `||`

Porque `&&` y `||` son correctos para 0/1 — que es como este lenguaje escribe un booleano — y
la suite los ejercita a propósito (`a && b` con (1,1), y `n == 2 || n == 3` dentro de un `if`).
`??` está mal para **todos** los tipos, así que no hay subconjunto seguro que conservar.

Lo medido, no supuesto:

- **nada en la suite ejecuta `??`**. Los cuatro `??` de `tests/` son el TypeScript del propio
  banco, una lista de tokens del léxico, y `e2e.test.ts` comprobando que la salida de
  **JavaScript** sigue diciendo `a ?? b` — un paso directo de un backend que nunca lo bajó.
- **implementarlo es trabajo de verdad**: `??` es una comprobación de nulo, no un opcode, así que
  necesita la bajada por ramas que el `? :` ya hace bien. Ese es el siguiente paso, y mientras
  no exista el rechazo es la respuesta honesta.

### Lo que queda abierto y por qué no se tapa

`||` y `&&` sobre **números que no son booleanos** siguen mal: `3 || 5` es 7, que es `3 | 5`.
No se niegan porque para 0/1 son exactos y negarlos rompería una característica que funciona;
queda escrito como **limitación conocida**, no como algo resuelto.

### Verificado

```

vecinos  `? :` numérico, `!`, `&&` y `||` sobre 0/1 siguen dando el valor correcto

```
